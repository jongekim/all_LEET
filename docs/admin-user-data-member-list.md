# 사용자 데이터 회원 목록 확장

2026-10-06 v1.8.0 릴리스. 탈퇴 후 모든 서비스 이력을 유지하고 관리자 목록에서만 `(탈퇴 회원)`으로 표시한다. 기존 게시글·댓글·채팅은 일반 이용자에게도 그대로 표시한다는 사용자 답변을 반영했다. 사용자의 계속 진행 요청에 따라 DB·함수·웹 순서로 운영에 반영한다. [적용 기록](admin-user-data-member-list-rollout.md)을 따른다.

- 표시: `이름 · 채점 12회 · 사설 3회 · 이메일`, 탈퇴 회원은 `이름 (탈퇴 회원) · 채점 12회 · 사설 3회 · 이메일`. 모바일의 횟수 잘림을 확인한 뒤 사용자가 이 순서를 승인했다. 옵션에서 UID를 숨기고 내부 선택·권한 검사·기존 상세 영역은 유지한다.
- 채점: 현재 KV `history:<UUID>`를 기존 `HistoryPage`와 같이 배열 순서의 첫 미처리 기록 기준 `groupTimestamp ?? timestamp` 차이 1초 미만으로 묶는다. 두 과목 함께 채점은 1회다. 삭제·예시·저장 실패는 제외한다.
- 사설: 현재 `mock_history:<UUID>` 배열의 항목 수. 키가 없으면 0, 손상된 구조·시각은 `확인 불가`다.
- 순서: 전체 대상의 `last_seen_at DESC NULLS LAST, UUID ASC`. 관리자·테스트 계정 포함, 마지막 이용 시각이 없으면 하단. 과거 로그인 시각으로 추정 복원하지 않는다.
- 기존 검색·select·50건 추가 로딩을 유지한다. 서버 정렬 후 해당 페이지의 건수만 계산하며 HMAC 커서는 관리자·검색어에 묶인 시각+UUID다. 페이지 사이 접속으로 위치가 바뀌면 클라이언트가 중복을 제거하고 재조회 때 최신 순서를 반영한다.
- 관리자 변경 완료 후 건수와 선택 사용자 정보를 갱신한다. 검색으로 선택 사용자가 빠져도 선택·편집 상태를 유지한다.

## 마지막 서비스 이용

`AppContent`의 headless `useServiceActivity`가 유지된 로그인 상태로 페이지 열기·이동, 탭 복귀, 실제 입력·클릭·스크롤·포커스를 관찰한다. 일반 사용자 JSX·문구·동선을 변경하지 않는다. 방치 heartbeat는 없으며 숨겨진 탭·계정 전환·로그아웃·언마운트 때 대기 작업을 제거한다.

운영 origin `https://all-leet.vercel.app`의 production 빌드만 활성화하며 로컬·preview는 비활성이다. 기존 통계의 관리자·테스트 제외/수집 스위치와 독립적이다. 입력 내용·활동 종류·이력·클라이언트 시각 없이 body `{}`를 전송한다. 요청과 서버 쓰기는 30초 단위로 합쳐 약 30초의 기록 지연·해상도 제한이 있다. 실패는 콘솔에만 기록한다.

`service-activity/touch`는 JWT의 실제 Auth 사용자만 서버 시각으로 갱신한다. body의 사용자 ID·시각은 거절하고 브라우저 Origin은 운영만 허용한다. `private.user_last_activity`는 RLS 활성화·일반 역할 접근 금지이며 service role만 접근한다. 두 공개 RPC도 service-only SECURITY INVOKER다. 목록 RPC는 관리자 권한을 재확인하고 응답과 조회 감사를 동일 트랜잭션에서 처리한다.

## 탈퇴 후 보관

마지막 이용 시각에는 Auth FK를 두지 않는다. `private.user_data_member_archive`는 활성 계정의 내부 UUID와 가입/확인 시각을 등록하는 서비스 소유자 기준표이며, 최초 탈퇴 시 이름·이메일·개인 `raw_user_meta_data`·가입/확인 시각·탈퇴 상태를 저장한다. 비밀번호·토큰·세션·인증용 app metadata는 복사하지 않는다. 기존 Auth UUID/시각을 최초 등록하며 새 Auth INSERT 트리거가 후속 계정을 등록한다. 이미 탈퇴했어도 KV·지원 분석·이용 원본/파생 이력·감사·이미지에 남은 UUID는 이름/이메일/최근 이용 시각 추정 없이 목록 기준표에 등록한다.

Auth DELETE와 최초 `deleted_at` 변경의 BEFORE trigger가 기존 값을 보관하고 관리자 권한을 회수한다. soft delete 후 물리 삭제는 이전 정보를 덮어쓰지 않는다. [Supabase soft delete 구현](https://github.com/supabase/auth/blob/master/internal/models/user.go)의 이메일/metadata 제거 전 정보를 캡처한다. Auth 트리거는 고정 테이블만 다루는 SECURITY DEFINER이고 빈 search_path와 직접 EXECUTE 차단을 적용한다. 보관 표는 RLS 활성화·일반 역할 접근 금지, service role은 SELECT와 이름/개인 metadata의 UPDATE만 허용한다.

원격 메타데이터로 확인한 12개 서비스 표의 `user_id` FK(문항 메모, 커뮤니티 6종, 채팅 프로필/메시지/제한, 공지 댓글/좋아요)를 Auth 대신 이 기준표에 연결한다. 기존 댓글·좋아요·신고의 게시글/댓글 관계와 개별 삭제 cascade는 유지한다. KV 기출/사설, 지원 분석/저장 진단, 이용 원본·파생 이력, 감사에는 Auth 삭제 cascade가 없고 그대로 보관한다. 이미지 경로·Storage metadata·실파일도 탈퇴 때문에 삭제하지 않는다. 자동 삭제/Cron을 추가하지 않으며 기존 통계의 90일/25개월 논리 조회 범위는 물리 삭제 정책이 아니다. 관리자 사용자 데이터 원본 조회는 남아 있는 전체 이력에 접근한다.

Auth 자체 계정과 인증 자료는 기존 탈퇴 처리에 따라 삭제한다. `private.admin_roles`의 Auth FK는 유지하며 soft delete에도 현재 권한을 회수한다. 만료 전 JWT가 남아도 활성 Auth 계정을 확인하는 제한적 RLS가 개인 메모 조회와 서비스 쓰기를 차단한다. 기존 소유자 RLS는 유지한다. Storage 이미지 INSERT/UPDATE/DELETE에도 같은 활성 확인을 추가하고 공개 읽기는 유지한다. service 전용 관리자 RPC와 소유자 기출/사설·지원 분석·통계 쓰기도 탈퇴 상태를 검사한다. 익명 공개 조회와 일반 회원의 기존 공개 게시글·댓글·채팅·이미지 조회를 바꾸지 않는다.

관리자 목록은 현재 Auth 계정·보관된 탈퇴 계정·기존 영구 분석만 남은 UUID를 중복 없이 포함하며 보관된 이름·이메일로 검색한다. 계정 상세는 기존 필드로 보관 정보를 읽는다. 탈퇴 계정 이름 수정은 기존 prepare/직접 `승인`/commit 절차로 보관 표를 원자 갱신하고, 활성 계정 이름은 기존 Auth 외부 작업을 사용한다. 이메일은 계속 조회 전용이다. 탈퇴 전 만든 미실행 계정 변경 승인은 탈퇴 상태 변경으로 충돌 처리한다. 실행/unknown 상태의 Auth 이름 변경은 최초 탈퇴 직전 실제 이름과 제안 값을 대조해 성공/실패를 확정하고 미완료 작업이 보관 계정 편집을 계속 막지 않게 한다. 뒤늦은 Auth 응답은 확정 결과를 덮어쓰지 않는다. 작업 행 → 계정 advisory lock 순서를 맞춰 경합을 방지한다. 명시적으로 승인한 관리자 개별 수정·삭제는 계속 가능하고 복구는 제공하지 않는다.

새로운 탈퇴 기능이나 계정 복구는 추가하지 않는다. 이미 사라진 정보는 소급 복원할 수 없으며 빈 이름·이메일을 임의 추정하지 않는다.

## 검증·적용

`20261006104150_user_data_recent_activity.sql` → 기존 `admin-user-data`와 새 `service-activity` → 웹 순서다. 이전 UUID 페이지 RPC는 남기며 새 API는 복합 서명 커서를 사용한다. 운영 적용 때 열린 관리자 페이지는 새로고침한다. 새로운 비밀값·환경 설정은 없다. 마이그레이션은 트랜잭션으로 적용하며 예상한 소유자 FK가 없으면 중단한다. Auth 등록/탈퇴와 기준표 초기화 사이 누락을 막는 Auth 테이블 잠금을 사용하고 잠금 대기가 5초를 넘으면 롤백한다. 적용 중 가입/계정 변경/탈퇴 쓰기가 잠시 대기할 수 있다. Auth 트리거/FK 교체와 RLS가 포함되므로 적용 전 현재 제약·정책을 다시 확인하고, 적용 후 테스트 계정의 생성/탈퇴·공개 조회·소유자 권한을 별도로 확인해야 한다. 원격의 Auth UPDATE/TRIGGER 권한과 `supautils.policy_grants`의 postgres → storage.objects 허용을 읽기 전용으로 확인했다. Storage 소유권은 바꾸지 않으며 정책 관리 권한은 [Supabase supautils 공식 설명](https://github.com/supabase/supautils#table-ownership-bypass)에 따라 재확인한다.

`test:user-data`는 합성 PostgreSQL의 묶음·전체 정렬·검색·50건 페이지·미접속 하단·역할 제한과 Deno 인증·커서 위조·Origin·행위자 제한을 확인한다. Vitest는 UID 숨김·0건/미가용·방치·복귀·계정 전환·StrictMode 정리를 확인한다. Playwright는 모바일/데스크톱 표시·페이지 추가·검색 시 선택 보존을 모의 Supabase로 확인한다. 운영 사용자 쓰기는 수행하지 않는다.

최종 전체 `npm run check` 통과: lint 오류 0/기존 경고 69, 단위 242, 기존 이력 Edge 100, 사용자 데이터 Edge 21, 통계 Edge 10, SQL 전체, 화면 E2E 84, 빌드 및 공개 HTML 10. 진행 중 Auth 이름 변경의 탈퇴 확정 처리를 포함한 v1.8.0 상태로 전체 검사를 다시 실행해 통과했다. 미실행 승인의 충돌과 실행/unknown 상태의 실제 이름 대조·뒤늦은 응답 무시·보관 계정 재편집을 합성 SQL에서 확인했다. 390px 화면에서 이메일 앞의 두 횟수가 모두 보이는 것을 직접 확인했다. 빌드 변경은 JS bundle 및 이를 참조하는 `build/index.html`이다. 운영 스키마 시험 적용과 전체 롤백, 정식 적용 후 합성 회원의 생성·soft/hard 탈퇴·원문 마이그레이션 이력·서비스 권한 검증을 통과했다. DB·함수 반영 및 웹 릴리스 절차는 적용 기록에 정리한다.

탈퇴 확장 SQL은 12개 실제 Auth FK를 합성 DB에 재현해 soft/hard 삭제 전후 전체 행 동일성, 타인 댓글·좋아요 보존, 계정 상세/승인 충돌/중복 실행, 이미지·이용·성적 보존, 공개 조회와 남은 JWT 차단을 검증한다. 화면 검증은 모의 서버의 탈퇴 표시·UID 숨김·횟수·이메일·새로고침 초기화를 포함한다.

화면 검증 중 기존 로그인 입력 테스트는 최초 서비스 워커 설치의 controllerchange 재탐색으로 값이 초기화되는 간헐 실패를 trace에서 확인했다. 읽기 전용 폼 테스트 모듈에서만 serviceWorkers를 차단하고 제품 코드/서비스 워커는 변경하지 않았다. 탈퇴 계정 상세 테스트는 제목과 필드에 같은 이름이 표시되므로 heading 역할로 대상을 한정한다.
