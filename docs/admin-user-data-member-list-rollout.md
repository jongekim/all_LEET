# 사용자 데이터 회원 목록 v1.8.0 운영 적용

2026-10-06 KST. 사용자의 개발·버전 관리 요청과 계속 진행 요청에 따라 Supabase `jkxxtyaanyhmjbdtybkp` 및 Vercel `all-leet`에 반영한다. 기능의 확정 범위는 [회원 목록 확장](admin-user-data-member-list.md)에 기록한다. 기존 사용자 화면 JSX·문구·동선은 유지하며 별도 기출 이미지·마크다운 작업과 로컬 캐시는 릴리스에서 제외한다.

## 버전·최종 품질

`npm run release:minor`로 1.7.0 → **1.8.0**을 적용하고 `npm run version:verify`를 통과했다. 최종 소스와 운영 통계 빌드 설정으로 `npm run check` 전체를 통과했다. lint 오류 0/기존 경고 69, 단위 242, 기존 이력 Edge 100, 사용자 데이터 Edge 21, 통계 Edge 10, 모든 SQL 검사, 화면 E2E 84, build, 공개 HTML E2E 10을 확인했다. 공개 통계만 조회해 83개 HTML을 생성했으며 브라우저의 운영 저장·삭제는 실행하지 않았다.

## DB 적용과 실제 권한

원격 main 기준은 `a0276177`이다. 변경 전 운영 컬럼·RLS·grants·함수·트리거·FK·14개 마이그레이션 이력을 읽기 전용으로 재조회했고 개발 기준과 일치했다. Auth와 Storage 소유권은 변경하지 않았다. Supabase의 `supautils.policy_grants`가 허용한 postgres의 Storage 정책 관리 권한을 사용했다.

`20261006104150_user_data_recent_activity.sql`을 시험 적용하고 새 UUID의 합성 회원만으로 검증한 뒤 전체 롤백했다. 기존 채팅 INSERT의 제한 행 생성과 게시글/댓글 작성 간격 트리거를 유지하며 합성 자료가 해당 조건을 충족하도록 했다. 기존 회원 데이터는 수정하지 않았다. 롤백 뒤 전체 스키마·정책·함수·FK·이력이 원래 상태와 동일함을 확인했다.

신규 SQL과 원문 마이그레이션 이력 1개를 같은 트랜잭션으로 정식 적용하고 PostgREST schema cache를 갱신했다. 전체 `db push`나 과거 이력 repair는 실행하지 않았다. Auth 등록/탈퇴와 초기화 사이 누락을 막는 Auth 테이블 잠금에 5초 제한을 적용했다. 가입·계정 변경·탈퇴 쓰기는 적용 중 잠시 대기할 수 있다.

정식 적용 후 같은 합성 검증을 전체 롤백으로 다시 통과했다. 12개 실제 소유자 FK, soft/hard 탈퇴 전후 서비스 행 동일성, 타인 댓글·좋아요 보관, 이름·이메일·개인 metadata, 기출 두 과목 1회·사설 횟수, 최근 이용 서버 시각·30초 제한, 지원 분석 보관, 탈퇴 전 승인 충돌, 진행 중 Auth 이름 작업 확정·늦은 응답 무시, 보관 이름의 직접 `승인` 수정, 공개 콘텐츠 조회, 활성 소유자 쓰기와 남은 JWT의 개인 메모 조회·게시글 쓰기 차단을 확인했다. Auth 트리거 2개와 제한적 RLS 15개가 존재하며 신규 두 RPC는 SECURITY INVOKER·service-role EXECUTE 전용이다. private 표의 RLS·일반 역할 접근 차단과 감사 변경 금지도 확인했다. 시험용 Auth·보관 계정이 남지 않음을 확인했다. 등록 이력의 SQL 원문은 저장소 마이그레이션과 일치한다.

보안 Advisor WARN 16개는 기존 항목과 동일하며 신규 WARN/ERROR는 없다. 새 private 표 2개는 일반 역할 접근을 의도적으로 허용하지 않으므로 `rls_enabled_no_policy` INFO를 보고한다. service role의 최소 권한만 사용하며 공개 허용 정책을 추가하지 않는다.

## 서버·웹 적용

DB 검증 후 변경된 `admin-user-data`와 신규 `service-activity`를 CLI 2.119.0의 API 번들링으로 먼저 배포했다. `verify_jwt=false`는 기존 구조와 동일하며 각 함수 내부에서 Supabase Auth로 실제 토큰을 검증한다. 운영 HTTP에서 최근 이용 기록의 익명·무효 JWT는 401, 허용하지 않은 Origin은 403, 운영 CORS preflight는 204였다. 기존 관리자·지원 분석·성적 API의 익명/무효 토큰 차단도 유지됐다. 인증된 운영 회원으로 실제 입력·저장·삭제는 실행하지 않았다.

신규 비밀값·환경 변수는 없다. 기존 GitHub Supabase 배포 설정을 재사용하며 main 함수 CI는 기존 성적 함수 다음 관리자/지원 분석/최근 이용/통계 함수를 배포한다. 웹은 위 준비 후 기능·DB·CI·문서·버전·빌드 산출물만 커밋하고 main 및 `v1.8.0` 태그를 push한다. 해당 커밋의 Vercel READY와 운영 HTML·정적 자산·모바일/데스크톱 공개 화면·관리자 로그인 경계 및 GitHub 함수 CI 결과는 최종 작업 보고에서 확인한다.

## 운영 경계

과거 접속 시각은 생성하지 않으며 새 웹을 사용한 이후부터 기록한다. 보관 정책은 반영 후의 탈퇴에 적용되고 이미 삭제된 정보는 복원하지 않는다. 새 탈퇴/복구 화면은 추가하지 않는다. 기존 관리자 탭은 새로고침해 새 목록과 커서를 사용한다. 관리자 개별 수정·삭제는 기존 직접 승인 후 영구 반영된다.

실제 관리자 JWT의 개인정보 화면, 외부 Auth 이름 수정과 Storage 실파일 업로드/삭제는 운영 계정으로 조작하지 않았다. 해당 UI/API 흐름은 모의 서버, Storage 정책은 실제 카탈로그와 합성 SQL로 검사했다. Auth 트리거는 실제 PostgreSQL에서 합성 Auth 행으로 검증했으며 Auth HTTP 탈퇴 호출은 실행하지 않았다.

웹 롤백은 DB·함수·이미 보관된 계정을 되돌리지 않는다. 신규 서비스 신원을 삭제하거나 FK를 Auth cascade로 임의 복구하지 않는다. 장애 시 관련 관리자 API와 최근 이용 기록을 제한하고 기존 소유자 저장·공개 콘텐츠의 호환성을 우선 확인한다.
