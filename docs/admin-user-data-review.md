# 관리자 사용자 데이터 개발 전 설계 검토

검토일: 2026-10-05 KST. 검토 대상: [설계안](admin-user-data-design.md). 이 문서의 F1~F9는 개발 전 검토 기록이다. 이후 확정 답변과 개발 요청을 반영해 구현했다. 현재 계약은 [설계](admin-user-data-design.md), 해결 방식·검증·운영 적용 경계는 [구현·운영](admin-user-data-implementation.md), v1.7.0 배포 상태는 [운영 적용 기록](admin-user-data-rollout.md)을 따른다.

## 검토 결론

관리자 인증을 유지하면서 선택 사용자 서비스를 주입하고 기존 표시 컴포넌트를 재사용하는 방향은 적합하다. 다만 기존 설계만으로는 영구 삭제·외부 계정 정보 변경·이용 이벤트 삭제의 실행 계약이 완성되지 않았다. 아래 필수 보완과 사용자 미정 사항을 닫은 뒤 기능별 개발 범위를 확정해야 한다.

검토에서 명확한 기술적 결함과 누락은 설계안에 보완했다. 설명 후 사용자 재답변으로 이메일 조회만, 이용 기록 조회·삭제만, 기출 식별자/회독/시각 고정을 확정했다. 남은 세부 운영/목업 선택은 임의로 결정하지 않았다. 문서 보완은 구현 검증 완료를 의미하지 않는다.

## 확인 범위와 근거

- 현재 네 가지 프로젝트 기본 문서, 관리자 선택/인가 처리, AuthContext, 채점·이력·차트·메모·지원 분석·커뮤니티·채팅 코드, 배포 대상 이력 함수, 통계 마이그레이션을 대조했다.
- 운영 Management API의 읽기 전용 SQL로 33개 테이블의 RLS/grants, 관련 함수, 34개 관련 제약, 마이그레이션 13개를 재확인했다. 실제 회원·성적·메모·게시글·이벤트 행은 읽지 않았다. 신규 지원 분석/관리자 변경 객체는 현재 없다.
- 운영 `private.product_usage_events`와 조회 감사 테이블의 service_role grants는 SELECT/INSERT/UPDATE이며 DELETE가 없다. KV의 broad grants와 RLS 정책 없음이라는 기존 경계도 그대로다.
- [Supabase 관리자 사용자 수정 문서](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid)는 관리자 수정이 확인 흐름 없이 직접 적용된다고 설명한다. 이 API를 호출하는 것만으로 새 이메일 소유자 확인이 생기는 것은 아니다.
- 순수 JavaScript 합성 사례로 중복 timestamp 삭제, 1초 이내 이력 묶음과 메모 연결 불일치, 삭제 이벤트 재수신을 검토했다. 실제 DB/API 실행 테스트가 아니다.

## F1. P1 — 기출 변경 대상을 시각만으로 확정할 수 없음

**문제:** `GradingResult`에 고유 기록 ID가 없고 기존 개별 삭제는 같은 timestamp의 모든 행을 제거한다. 목록은 1초 이내 시각을 묶지만 `TrendChart`는 학년도+정확한 groupTimestamp로 묶고 `ResultPage` 메모는 첫 결과의 정확한 시각만 사용한다. 이 세 가지를 하나의 동일 그룹 규칙이라고 설명한 초안은 부정확했다.

**재현:** timestamp가 같은 두 과목에서 한 항목만 선택해도 기존 timestamp DELETE는 둘 다 제거한다. groupTimestamp 1000/1300인 두 항목은 목록에서 한 묶음이지만 첫 시각 메모 조회로는 1300의 메모를 찾지 못한다.

**필수 보완:** 표시 규칙을 사용자 화면과 일치시키는 것과 원본 변경 단위를 분리한다. 변경 참조는 서버가 서명한 KV 키·원본 스냅샷 해시·정확한 배열 위치/원본 해시·선택 항목 집합으로 구성한다. 배열 위치만 받지 않는다. commit 잠금 안에서 같은 스냅샷인지 확인하고 달라지면 충돌로 반환한다. 기존 JSON에 ID를 소급 추가하거나 원본 기록을 합치지 않아도 이 방식으로 정확한 변경 단위를 만들 수 있다.

**메모:** 삭제할 원본 항목마다 정확한 user_id·groupTimestamp/호환 timestamp·subject의 합집합을 산출한다. 한 과목 삭제와 두 과목 묶음 삭제의 단위를 UI 계약에서 확인한다. 범위가 모호한 옛 기록은 임의 인접 시각으로 메모를 삭제하지 않는다.

## F2. P1 — DB 행 잠금만으로 신규 KV·연쇄 삭제 경합을 막지 못함

**문제:** 기존 사용자 POST/DELETE는 읽기→배열 저장의 두 요청이다. 관리자만 원자 갱신해도 과거 사용자 쓰기가 덮어쓸 수 있다. KV 키가 아직 없는 첫 저장에는 잠글 행도 없다. 게시글의 연관 데이터는 승인 후 다른 사용자가 추가할 수 있다.

**필수 보완:** 사용자·관리자 KV 쓰기 모두 동일한 서버 원자 RPC로 전환하고 KV 키별 transaction advisory lock을 행 존재 여부와 무관하게 먼저 획득한다. 기존 URL/응답/회독 의미는 보존한다. 조회/수정 배포 전 기존 쓰기 경로가 모두 이 계약을 사용하는지 검증한다.

게시글 삭제에서는 commit 트랜잭션의 잠금으로 부모·댓글·참여 관계에 대한 관련 INSERT/DELETE/UPDATE와 경합을 막은 뒤 정확한 영향 목록을 재검사한다. FK의 일반 잠금만으로 모든 UPDATE/DELETE도 차단된다고 가정하지 않는다. 구현 SQL에서 필요한 잠금 순서/격리를 정하고 대기 뒤 재조회가 승인 목록과 다르면 재승인한다. 집계 발행과 이용 이벤트 수집도 같은 영향 날짜/사용자 잠금 계약을 검토한다.

## F3. P1 — 승인 challenge·중복 실행·외부 감사 계약이 불완전함

**문제:** 일회용 challenge와 idempotency ID만 적혀 있어 승인 소비→실제 갱신 사이의 실패와 동시 재전송을 어떻게 처리할지 불분명하다. Auth/Storage는 DB 감사와 같은 트랜잭션으로 묶을 수 없다.

**필수 보완:** 관리자·대상·작업·원본 버전·payload/영향 해시에 묶인 서버 operation ID와 상태를 둔다. DB 작업은 challenge 소비·중복 실행 판정·현재 역할/영향 검사·원본 갱신·감사를 한 트랜잭션으로 처리한다. 같은 operation의 재요청은 새 변경 없이 상태만 돌려준다.

Auth 작업은 감사 가능한 실행 의도를 먼저 영속 저장하고 외부 호출 후 결과를 기록한다. 결과 기록 전에 프로세스가 중단되면 unknown 상태로 두고 실제 Auth 상태와 대조하며 새 작업처럼 반복하지 않는다. 파일 삭제는 DB 원본 삭제와 정리 작업 등록을 한 트랜잭션으로 처리하고, 승인된 경로만 실제 삭제한다. 외부 호출 시작 후 로그아웃했다고 이미 진행된 변경이 취소된다고 표시하지 않는다.

입력한 문자열 `승인`은 사용자의 실수 방지 UX다. 서버는 승인 operation의 범위를 검증할 수 있지만 실제 키보드 타이핑 여부를 암호학적으로 증명하지는 못한다. 인증/권한 경계를 문자열 검사로 대체하지 않는다.

## F4. P1 — 이용 이벤트 수정/삭제는 단순 CRUD로 구현할 수 없음

**문제:** 최초 이용 anchor와 일별 활동/발행 자료는 별도 저장되고 원본이 없어진 과거를 다시 계산할 수 없다. 수집 품질의 accepted/duplicate 등은 데이터 보관 개수가 아니라 당시 접수 사실이다. 삭제 이벤트가 재전송되면 기존 `ON CONFLICT DO NOTHING`은 삭제된 unique key를 찾지 못해 재수용할 수 있다. 원격 service_role에는 원본 DELETE 권한도 없다.

**사용자 재답변:** 이용 기록은 조회·삭제만 허용하며 내용 수정은 제외한다. 이전의 이벤트 직접 편집 요구를 대체한다. 다만 삭제에도 아래 정합성 처리는 필요하다.

**필수 보완:** 내용 수정 API를 만들지 않는다. 파생 집계는 직접 숫자를 덮어쓰지 않고 동일 지표 규칙으로 재생성/무효화한다. 최초 이용의 역사적 근거를 복원할 수 없으면 known=false 등 보수적인 미가용 상태로 만든다. 접수 품질 counters를 현재 원본 개수로 다시 계산하지 않는다.

삭제 전에 event_id와 actor_scope+semantic_key의 비복구성 중복 방지 표식을 남기고 ingest가 확인하도록 한다. payload·답안·원본 본문을 남기는 복구 백업과 구분한다. 신규 DELETE 권한은 필요한 원본에만 부여하고 관리자 감사에는 부여하지 않는다. 삭제 표식의 보존/전송 재시도 가용 기간도 상세 계약에서 정한다.

현재 보관된 개인 원본의 조회에 기존 통계 분석 90일 제한을 자동 적용하지 않는다. 오래된 보관 원본을 삭제했을 때 파생 자료를 정확히 재생성할 수 없다면 미가용/지원 범위를 명시해야 한다. 원본 삭제 기능과 장기 집계 정합성 검증을 같은 개발 단위에 넣는다.

## F5. P1 — 이메일은 기존 관리자 API 선택과 사용자 확인 정책이 충돌할 수 있음 (정책 해결)

**문제:** 초안은 이메일 변경 확인 방식을 미정으로 두었지만 서버 관리자 API를 동시에 제안했다. `updateUserById`는 직접 적용이며 기존 로그인은 email_confirmed_at도 검사한다. 이메일 변경 뒤 로그인 가능 여부와 확인 상태를 따로 검증해야 한다.

**필수 보완:** 이메일 편집 제외/새 소유자 확인 후 적용/관리자 승인 후 즉시 적용 중 설명 후 재질문으로 확정한다. 확인 후 적용을 선택하면 즉시 관리자 update만 호출하는 구현은 불가하며, 별도 pending 상태·주소 소유 확인·최종 Auth 적용 흐름을 설계해야 한다. 대상 사용자 토큰으로 로그인하거나 관리자의 `updateUser`를 호출해서 대신 처리하지 않는다.

**사용자 재답변:** 이메일은 조회만 허용한다. 이전 이메일 편집 허용을 대체하고 이메일 변경 API/UI를 범위에서 제외했다. 확인 메일·즉시 주소 변경 계약은 구현하지 않는다. 서버 필드 허용 목록에서 이메일·email_confirm도 제외하고 직접 요청이 차단되는지 검사한다.

이름은 user_metadata의 name 필드만 변경하고 birth_date/university 등 다른 metadata를 보존한다. 닉네임 UNIQUE 충돌과 이름 변경 Auth 응답 유실을 검증한다. Auth 관리자 API에 없는 compare-and-swap을 가정하지 않고 외부 계정 동시 변경의 한계를 명시한다.

## F6. P1 — 재계산 항목의 의존성과 규칙 버전이 빠져 있음

**문제:** `gradeAnswers`는 답안부터 정답 수·분야 분석·표준점수·백분위·보정점수까지 한꺼번에 계산하고 timestamp/round도 새로 만든다. 이 결과를 spread하면 선택하지 않은 필드와 식별자까지 덮어쓴다. 정답률은 저장 필드가 아니라 correct/total로 계산되는 표시 값이다.

**필수 보완:** 재계산용 임시 결과와 저장 patch를 분리한다. 선택한 필드만 patch하고 timestamp·groupTimestamp·round는 보존한다. 정답률만 따로 저장하는 칼럼을 만들지 않는다. 직접 수정과 재계산을 같은 필드에 동시에 지정하면 우선순위를 임의로 고르지 않고 요청을 거절해 선택을 정리하게 한다.

표준점수/백분위는 어떤 correct를 입력으로 쓸지, 보정점수는 어떤 standardScore를 쓸지 명시한다. 최신 규칙/저장 당시 규칙 중 적용 버전도 명시하며, 버전 자료가 없으면 재계산 불가로 반환한다. 답안·정답 수·점수 간 수동 불일치는 사용자가 허용한 범위에서 보존하지만 숫자 범위/유한성/문항 번호 등 구조 검증은 유지한다.

## F7. P2 — 모든 개인 데이터의 조회 목록과 기존 화면 재사용 책임이 불완전함

**문제:** AuthContext는 name 외 birth_date/university도 저장하지만 조회 표에는 빠졌다. 커뮤니티에는 내 참여 전용 화면이 없고 ChatPage는 최근 전체방 50개·프로필 자동 생성·Realtime 구독을 실행한다. 기존 페이지를 통째로 붙여서는 개인 전체 자료와 순수 열람을 만족하지 못한다.

**필수 보완:** 생년월일/대학교를 제한된 계정 상세 조회에 추가하고 편집은 승인된 이름/닉네임/이메일만 허용한다. 임의 Auth metadata 전체 덤프는 하지 않는다. 저장된 기존 기록에는 관리자 생성 표시가 없다는 이유로 제외하지 않는다.

기존 카드/메시지/결과의 표시 컴포넌트를 추출하고 관리자 개인 목록/페이지네이션을 별도 조립한다. 자기 작성/좋아요/신고의 목록과 주변 타인 맥락을 구분하고 모든 관계 요청에 target 소유자 검사를 둔다. Realtime을 사용한다면 계정/대상/인가 세대에 묶고 제거 시 unsubscribe한다. profile ensure·조회 수 증가·usage tracking 등 기존 효과를 그대로 가져오지 않는다.

## F8. P2 — 지원 분석 저장 실패 진단의 독립 경로와 보존 계약이 빠져 있음

**문제:** 일반 분석은 UI를 바꾸지 않고 비동기 저장해야 하지만 실패 결과는 관리자에게 보여 줘야 한다. 기존 이용 통계는 관리자·테스트 계정을 제외하고 수집 중단도 가능하므로 그 이벤트만으로 저장 실패를 추적하면 요청 범위의 일부를 누락한다.

**필수 보완:** 계정/실행 ID·관측 상태·안전한 오류 코드의 지원 분석 저장 진단을 별도 운영 경로로 설계한다. 입력/점수/결과를 통계에 복사하지 않는다. 결과 원본은 동일 execution ID로 idempotent 저장하고 수정/삭제된 실행이 뒤늦은 재전송으로 복원되지 않게 비복구성 실행 표식을 유지한다. 규칙 버전이 달라지면 클라이언트에 이미 표시한 결과와 서버 재계산의 동일성도 검증한다.

지원 분석 보존 기간/탈퇴 처리/실패 진단 보존은 아직 미정이다. UI 유지 때문에 오프라인·탭 종료까지 무조건 서버 저장되거나 실패가 완전히 관측된다고 보장할 수는 없다. 확인된 저장 성공/실패/unknown과 관측 불완전을 구분한다.

## 개발 착수 기준

| 순서 | 완료할 내용 |
|---|---|
| 1 | 재답변 반영 완료: 이메일 조회만·이용 기록 조회/삭제만·기출 식별자/회독/시각 고정 |
| 2 | F1~F6의 참조/잠금/승인 operation/외부 작업/재계산 계약과 필요한 DB 권한 확정 |
| 3 | 닉네임 과거 반영·지원 분석 규칙/보존/탈퇴·타인 맥락·새로고침 등 남은 사용자 선택 확정 |
| 4 | 합성 자료 분리 목업에서 화면 재사용·새 관리자 제어·실데이터 0건·승인 영향 목록 검토 |
| 5 | 기존 쓰기 원자화 → 관리자 조회 → 제한된 변경 → 이용 기록 삭제/지원 분석 순서로 개발 단위를 나누고 매 단위 검증 |

전 기능이 실제 준비되기 전에 미지원 메뉴를 정상 동작하는 기능처럼 연결하지 않는다. 위 순서는 사용자 기능 범위를 축소하지 않는 개발 순서 제안이며 운영 적용/배포 승인이 아니다.

## 필수 회귀 시나리오

1. 중복 timestamp, 서로 1초 이내인 다른 회차, 한 과목 기록, 동일 시각 다른 사용자, 원본 배열 변경 뒤 오래된 참조.
2. KV 첫 저장 동시 두 건, 사용자 저장 중 관리자 삭제, 묶음 삭제 중 감사 실패, 옛 함수 쓰기 경로가 남은 배포.
3. 게시글 승인 후 댓글/좋아요 추가 또는 삭제, 기존 댓글 내용 변경, 같은 건수로 관계 대체, 이미지 URL 경로 소유자 불일치.
4. challenge 소비 직전 중복 commit, DB rollback, 응답 유실 뒤 상태 확인, Auth 성공 뒤 결과 기록 실패, 작업 중 권한 회수.
5. 이벤트 삭제 후 같은 UUID/semantic key 재전송, 삭제와 수집/발행 경합, 최초 이용 삭제 뒤 원본 근거 불가, 수집 품질 보존, 직접 이벤트 수정 요청 거절.
6. 답안만/점수만/분야만/보정만 수정, 같은 필드 수동·재계산 충돌, 규칙 버전 없음, 지원 분석 서버/클라이언트 버전 차이.
7. 관리자·테스트 계정의 지원 분석 실패 진단, 로그아웃/다른 계정 전환, 저장 성공 응답 유실, 관리자 삭제 후 늦은 원래 실행 재수신.
8. metadata name 수정 뒤 birth_date/university 보존, 닉네임 UNIQUE, 직접 이메일 변경 요청 거절, 사용자 화면/목록/차트 값과 관리자 표시 일치.

검토 증거는 코드/원격 메타데이터와 합성 사례다. 애플리케이션 테스트와 운영 기능 검증을 통과했다고 해석하지 않는다. 문서만 변경했으므로 이 작업에서는 npm 품질 게이트·빌드·운영 쓰기를 실행하지 않는다.
