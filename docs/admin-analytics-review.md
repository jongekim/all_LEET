검토일: 2026-10-03 KST. 대상: [전체 설계](admin-analytics-design.md), [PWA 설계](admin-pwa-analytics-design.md).

2026-10-04 추가된 대시보드·장기 기간을 포함한 최신 검토는 [통합 재검토](admin-analytics-review-20261004.md)를 따른다. 최신 검토의 네 보완안은 설계 본문·API 계약·인수 기준에 반영했으며 앱·예시 HTML에는 아직 미반영이다. 아래는 기존 검토·반영 이력이다.

**반영 상태: 2026-10-03 최초 검토 및 재검토 설계 반영 완료. 2026-10-04 로컬 구현 반영, 운영 미적용.** 사용자가 검토 개선사항 반영을 요청하여 1장의 여섯 보완안과 2장의 관리자 조회 이력, 5장의 재검토 네 항목을 두 설계의 본문·API·데이터 책임·구현 순서·인수 기준에 통합했다. 아래 1~4장은 최초 반영 전 문제와 제안의 근거를 보존한 기록이며, 현재 구현 기준은 재검토를 반영한 두 설계 본문이다.

세션 유지 보완에서는 서버가 입력 중임을 알 수 있도록 로컬 활동 상태를 개별 조작 대신 최대 분당 한 번의 최소 `session_activity`로 보고하는 계약까지 구체화했다. 이는 기능 이용 이벤트와 구분하며 활성·이용·재방문 수를 늘리지 않는다. 기록 보존 기간은 기존 제안값을 유지하고 비교/조회 범위를 실제 가용 데이터로 제한한다. 기간 확대·운영 삭제는 실행하지 않았다.

검토 결론: 요구하는 기능 범위는 충분하다. **수집 의미·흐름 연결·세션·조회 가능 기간**을 우선 보완하는 것이 중요하다. 회원 식별과 PWA 구분 요구는 유지한다. 아래는 설계 검토 당시의 판단 기록이다. 이후 사용자 UI 승인 및 개발 요청으로 로컬 구현을 추가했으며 현재 상태는 [구현·운영 문서](admin-analytics.md)를 따른다.

## 1. 우선 수정할 부분

### 1.1 백그라운드 조회와 실제 화면 이용을 명시적으로 구분

근거: [App.tsx](../src/App.tsx) 77행은 모든 경로에서 `useUserHistory`를 사용하고, [useUserHistory.ts](../src/hooks/useUserHistory.ts) 55~60행은 로그인 회원의 공식·사설 이력을 자동으로 불러온다. [HistoryPage.tsx](../src/pages/HistoryPage.tsx) 399행은 과거 이력을 `/result`로 보내며, [ResultPage.tsx](../src/pages/ResultPage.tsx) 104~119행은 같은 경로에서 새 계산·과거 결과·결과 없음 상태를 처리한다.

현재 설계는 이력 정상 표시와 새 실행 연결을 요구하지만 계측 위치·진입 출처 계약이 구체적이지 않다. 공통 API 성공이나 `/result` 경로 진입만 계측하면 홈 방문이 이력 이용으로, 과거 결과 재조회가 새 채점으로 집계될 수 있다.

수정 제안:

- `history_viewed`는 해당 공식/사설 이력 화면이 실제 표시되고 조회 상태가 정상일 때 발생한다. `useUserHistory.load()`의 성공 자체에는 이용 이벤트를 붙이지 않는다.
- 결과에는 `entry_source=new_grading|history|example|unknown`을 붙인다. 현재 코드가 이 값을 제공한다고 가정하지 않고 실제 구현 때 navigation state 등 내부 연결 정보를 추가한다.
- `grading_result_viewed`는 새 계산의 `grading_run_id`가 연결된 정상 결과에만 발생한다. 과거 결과는 별도 결과 조회 행동으로 기록한다. 결과 없음 화면은 정상 결과 조회로 집계하지 않는다.
- 빈 이력 화면을 정상 조회한 경우는 화면 이용에 포함하고, 이력이 실제 존재하는 회원 수와 따로 표시한다.

인수 사례: 로그인 후 홈만 열기 → 이력 이용 0회. 과거 이력 상세 두 번 보기 → 과거 결과 조회 2회, 새 채점 0회. 결과 없이 `/result` 진입 → 정상 채점 결과 조회 0회.

### 1.2 입력 시작과 채점 실행 사이의 연결 ID·완료 기준 확정

현재 `grading_input_started`는 입력 흐름 ID, 요청·완료·결과는 채점 실행 ID로 중복 제거하지만 두 ID의 관계와 조회 기간 끝에서의 완료 관찰 기준은 미정이다. 같은 세션에서 답안을 초기화하거나 여러 번 채점할 때 어느 입력의 결과인지 연결해야 한다.

수정 제안:

- 첫 답안 입력 때 `input_flow_id`를 만들고 학년도·문형 변경, 답안 전체 초기화, 기존 흐름을 폐기하는 조건을 명시한다.
- 유효한 채점 요청 때 새 `grading_run_id`를 만들고 해당 `input_flow_id`와 연결한다. 계산·과목별 저장 시도·결과에 같은 실행 ID를 전달한다.
- 같은 흐름에서 재채점은 새 실행으로 센다. 입력 시작 세션의 전환율은 해당 흐름의 실행 중 정상 결과를 본 세션을 한 번만 센다. 실행별 계산 완료율은 실행을 분모로 별도 계산한다.
- 조회 기간 끝 직전에 시작한 흐름은 아직 완료 여부가 결정되지 않을 수 있다. 최초 버전은 30분 비활동으로 닫힌 세션만 완료/미관측 비율의 분모로 사용하고 진행 중 세션 수를 따로 표시한다. 아직 집계되지 않은 늦은 이벤트도 명시한다.
- 기간은 입력 시작 시점을 기준으로 고정하고, 같은 세션에서 조회 종료 이후 발생한 결과도 확보된 데이터 범위에서 연결한다. 관찰이 끝나지 않았으면 미확정으로 남긴다.
- 결과 이벤트가 없다는 사실만으로 사용자가 의도적으로 포기했다고 단정하지 않는다. 이탈 지표는 **결과 조회 미관측**이라는 정의를 함께 제공한다.

인수 사례: 입력 → 초기화 → 다른 시험 입력 → 채점, 동일 입력 재채점, KST 자정 직전 입력 후 다음 날 결과 조회, 진행 중 세션, 결과 이벤트만 누락된 경우.

### 1.3 긴 답안 입력 중에도 세션이 유지되게 정의

현재 최소 수집 계약은 첫 답안 입력을 한 번만 기록한다. ‘마지막 서버 이벤트 이후 30분’을 비활동으로 사용하면 사용자가 계속 70문항 답안을 입력해도 세션이 끊어져 입력 시작과 결과가 다른 세션이 될 수 있다.

수정 제안:

- 세션의 비활동은 서버 전송 이벤트 간격과 구분한다. 화면이 보이는 동안 실제 답안 변경·선택·기능 조작이 있으면 로컬 `last_interaction_at`을 갱신한다.
- 이 갱신을 위해 개별 답안·키 입력·모든 클릭 기록을 서버에 보내지 않는다. 세션 유지에 필요한 시각만 로컬에 보관하고 실제 기능 이벤트 발생 시 세션을 확정한다.
- 가만히 열린 탭, 단순 포커스, SW 업데이트만으로 활동 시각을 계속 갱신하지 않는다. 백그라운드에서 재개되었을 때는 마지막 실제 조작과의 간격을 확인한다.
- 새로고침·같은 채널의 다른 탭·PWA 복귀에서 저장소 접근 실패가 있으면 정확한 세션 연결이 불가능한 상태를 표시하고 별도 관측 세션으로 처리한다.

인수 사례: 40분 동안 계속 답안 입력 후 채점 → 같은 입력 세션. 40분 동안 조작 없이 방치 후 채점 → 새 세션. 해당 차이를 채점 재실행이나 새 회원으로 해석하지 않는다.

### 1.4 수신 시각과 활동 시각·순서를 분리

현재 계약은 서버 `received_at`과 허용 범위의 상대 순서를 사용한다. 배치·재시도에서 실제 클릭과 수신이 달라지므로 회원 타임라인을 실제 행동 시각처럼 표시하거나 완료 순서를 수신 순서로 정렬하면 오해가 발생한다.

수정 제안:

- `received_at`은 서버 수신 시각으로 그대로 보존한다. 클라이언트 `occurred_at`, 문서별 `page_instance_id`와 증가하는 `event_sequence`, 실행 ID를 함께 기록하는 계약을 추가한다.
- 회원 타임라인에는 **관측된 활동 시각**과 수신 시각·지연 여부를 구분해 표시한다. 클라이언트 시각은 검증된 서버 시간이라고 표시하지 않는다.
- 첫 버전의 일별 집계는 서버 수신 시각 기준으로 일관되게 유지하고 화면에 기준을 표시한다. 추후 활동 시각 기준으로 바꿀 때는 보정·늦은 이벤트 재집계·버전 변경을 함께 설계한다.
- 같은 문서 안에서는 실행 ID·이벤트 순서로 흐름을 연결한다. 서로 다른 탭의 순서는 증가 번호만으로 비교하지 않는다. 유효하지 않은 시각·순서는 시간/전환 분석에서 미확인으로 분류하되 기록 자체를 정상 이용 0건으로 바꾸지 않는다.
- 짧은 계산·저장 대기 시간을 추가로 측정할 경우 단조 시계 기반 경과 시간을 쓴다. 절대 시각과 구분하며 PWA 장시간 백그라운드·기기 잠자기 동안 같은 타이머가 동일하게 동작한다고 가정하지 않는다. [MDN Performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)

인수 사례: 수신 순서 역전, 같은 배치의 입력/결과 이벤트, 시계 오차, 자정 전 행동의 자정 후 수신, 여러 탭 동시 이용.

### 1.5 이전 기간 비교와 세션 집계가 보존 범위를 넘지 않게 수정

현재 설계는 최근 90일 조회·이전 같은 길이 기간 비교를 제공하면서 원본 보존은 90일이다. 이전 90일 원본이 없는데 0으로 비교하거나 일별 고유 세션 수를 더하면 잘못된 이용량·증감이 나온다. 회원은 DISTINCT 계산이 명시되어 있으나 세션·실행의 기간 중복 제거는 더 명확해야 한다.

수정 제안:

- 지표별 `available_from`, `available_through`, `coverage_status=complete|partial|unavailable`을 반환한다. 수집 시작일, 원본/활동일/집계의 서로 다른 보존 기간과 정의 버전 구간을 반영한다.
- 현재와 비교 기간이 모두 같은 정의·필터로 완전하게 조회되는 경우에만 증감률을 제공한다. 부족한 기간은 ‘비교 데이터 없음/일부 기간’으로 표시하고 0으로 채우지 않는다.
- 세션·회원·채점 실행의 기간 총합은 각 식별자를 전체 기간에서 DISTINCT 처리한다. 자정을 넘는 같은 세션은 각 날짜에 나타날 수 있지만 선택 기간 전체에는 한 번만 센다.
- `product_usage_daily`에는 가산 가능한 행동 횟수만 합산한다. 일별 고유 세션·회원 요약은 기간 전체 고유 수를 복원하는 근거로 쓰지 않는다.
- 로그인 여부가 바뀐 같은 세션은 두 부분집합에 등장할 수 있다. 로그인/비로그인 세션 수의 합이 전체와 반드시 같다고 주장하지 않는다.
- 같은 표의 학년도·과목 필터도 시험 메타데이터가 있는 행동에만 적용한다. 메타데이터 없는 전체 페이지뷰를 시험 이용률의 분모에 섞지 않고 해당 시험 입력/선택이 관측된 세션으로 정의한다.
- 상세 활동 90일, 회원 활동일 180일, 전체 집계 13개월은 아직 제안이다. 상세 타임라인도 더 오래 필요한지는 구현 전에 확정할 운영 선택이며 자동으로 보존 기간을 늘리거나 삭제 작업을 만들지 않는다.

인수 사례: 90일 조회의 이전 90일 비교, 수집 시작일을 걸친 7일 조회, 자정을 넘는 세션, 로그인 전후 세션, 학년도 필터와 전체 방문의 분모 구분.

### 1.6 실제로 측정할 수 있는 수집 품질만 표시

현재 전체 설계 8장의 ‘수집 차단·저장소 사용 불가·식별 실패 비율’은 모수 정의가 없다. 수집 코드가 차단되거나 전송 전에 페이지가 끝나면 자체 서버에 기록 자체가 오지 않으므로 전체 누락률이나 차단률을 정확히 계산할 수 없다.

수정 제안:

- 서버가 받은 제출 건수, 수락/중복/유효성 거절/인증 실패/처리 실패 건수와 비율을 제공한다. 수락은 서버 저장 성공을 확인한 것만 포함한다.
- 일부 배치만 저장되었을 때 이벤트 ID별 결과 또는 원자적 배치 저장 중 한 방식을 계약에 고정한다. 단순 HTTP 2xx를 모든 이벤트 수집 성공으로 해석하지 않는다.
- 미도달 이벤트의 전체 누락률은 ‘측정 불가’로 표시한다. 클라이언트 오류 보고가 도달하면 관측된 오류 건수로 제공하고 전체 사용자의 비율로 확대하지 않는다.
- Vercel 방문과 자체 세션 차이는 식별·정의·지원 환경의 차이도 포함하므로 바로 광고 차단률로 계산하지 않는다.
- 이미 설계된 집계 마지막 성공 시각·지연 표시와 함께 제공한다. 처음부터 알림·감시 자동화·실시간 접속자 기능까지 늘릴 필요는 없다.

## 2. 추가 기능은 하나만 추천

**관리자 회원 기록 조회 이력**을 추천한다. 현재 관리자 권한 검사는 있지만 어느 관리자가 어느 회원의 기록을 언제 조회했는지는 남기도록 정의되어 있지 않다. 실제 이름·이메일을 보여주는 요구가 추가되어 이 기능의 필요성이 생겼다.

- 서버에서 검증한 관리자 `user_id`, 대상 회원 `user_id` 또는 세션, 조회 종류·기간·필터·시각·반환 건수를 기록한다.
- 회원 검색은 검색 종류·검색 수행 여부를 기록하고 이름·이메일 검색어를 또 다른 원본 로그에 복사하지 않는다.
- 조회 이력은 관리자 API 접근/응답 제공 기록이다. 화면을 실제 읽었다거나 내보내기를 완료했다는 증거로 이름 붙이지 않는다. 브라우저가 보고하는 관리자 ID를 신뢰하지 않는다.
- 비공개 서버 객체와 기존 관리자 인가를 사용한다. 이용자 기능 이벤트와 분리해 방문·채점·재방문 수를 늘리지 않는다.
- 관리자 전용 응답의 메모리/서버 캐시를 읽는 API 요청도 같은 기록 기준을 적용한다. 별도 알림·승인 과정은 제안하지 않는다.

사용자의 개선사항 반영 요청에 따라 관리자 조회 이력을 최초 출시 설계에 포함했다. 테이블·화면·로그 수집은 아직 구현하지 않았다.

## 3. 이번에 늘리지 않아도 되는 범위

실시간 접속자·전면 세션 녹화·모든 클릭 수집·개인 점수 대시보드·전체 설치 대수 추정은 현재 목적을 달성하는 데 필요하지 않다. 기존 회원별 기록, PWA 분석, 기능·채점·재방문 지표의 정확도를 먼저 확보한다.

이미 적절하게 반영된 사항은 실제 회원 ID 유지, PWA/브라우저 중복 제거, 설치 클릭과 실제 이용 구분, 로그인 전 익명 기록을 무리하게 실명 회원에게 귀속하지 않는 방식, 저장 응답 미확인과 확정 실패 구분이다. 이 방향은 유지한다.

## 4. 검증 범위와 다음 적용

현재 앱 코드와 두 설계 문서를 대조했다. 브라우저 타이머의 특성은 공식 문서로 확인했다. 원격 스키마의 신규 변경 여부를 다시 확인하거나 회원/답안 데이터를 조회하지 않았으며, 구현 없는 문서 검토이므로 빌드·E2E·DB 쓰기 검증은 실행하지 않았다.

이 검토는 근거 기록으로 남기며 1·2장의 계약과 아래 5장의 재검토를 전체/PWA 설계에 통합했다. 상세 활동 보존 기간은 기존 90일 제안값을 유지하고 최초 이용일 요약 보존만 별도 계약으로 구분한다. 최종 운영 기간은 구현 전 확정한다. 기존 앱 UI 변경에는 저장소의 승인 규칙을 유지한다. 설계 문서 통합·링크·형식·반영 상태를 검증했고 구현이 없어 빌드·E2E·DB 쓰기 검증은 실행하지 않았다.

## 5. 재검토 네 항목과 반영 결과

### 5.1 상태 전송 중단과 관찰 종료 구분

문제: 실제 조작이 없으면 상태 전송도 멈추는데, 전송 중단을 미확정으로만 처리하면 정상 이용 종료 세션도 전환율 분모에서 계속 빠진다.

반영: 서버의 마지막 새 활동 수신 후 30분 open, 추가 15분 grace, 이후 알려진 수집 장애가 없으면 observation_closed로 처리한다. 여러 탭의 마지막 상태를 합치고 중복은 시각을 연장하지 않는다. 알려진 수집 장애는 uncertain이며 늦은 자료·장애 복구 때 다시 판정/집계한다. 관찰 종료는 확보된 자료의 판정으로 표현하고 실제 종료·완전한 수집을 증명하지 않는다. 로컬 세션의 30분 비활동 규칙은 유지한다.

### 5.2 남아 있는 답안을 새 세션에서 재개

문제: 답안을 남긴 채 40분 뒤 채점하면 세션은 바뀌고 입력 흐름은 이전 세션에 남아 새 결과와 입력 단계가 연결되지 않는다.

반영: 다음 실제 답안 수정/유효 채점 요청에서 새 입력 흐름과 `grading_input_resumed`를 만들고 새 세션의 전환 분모에 한 번 포함한다. 이전 세션의 미관측을 성공으로 바꾸지 않는다. 단순 복귀는 이벤트를 만들지 않고 답안은 유지한다. 이전 흐름 연결은 동일 계정/계속 비로그인인 동일 저장소·채널에서만 허용하고 로그인·로그아웃·계정 변경·분리된 저장소에서는 연결하지 않는다.

### 5.3 회원 전환·재방문 기준일 통일

문제: 화면 설명의 가입 후 7일/최초 채점일과 계산 정의의 확인 후 7일/최초 핵심 이용일이 달랐다.

반영: 첫 채점 전환은 계정 확인 완료 후 7×24시간, 서비스 재방문은 최초 핵심 이용 KST 날짜, PWA 재방문은 최초 PWA 핵심 이용 KST 날짜로 통일한다. 가입일·최초 채점일·일반 PWA 첫 이용일은 각기 별도 값이다. 동일한 지표 이름에 다른 시작점이 들어가지 않게 화면 제안·계산 정의·인수 기준을 맞췄다.

### 5.4 최초 이용일 요약과 순환 보존 분리

문제: 원본/회원 활동일 만료 뒤 최근 자료의 MIN만 계산하면 기존 회원을 신규 PWA 회원이나 새 최초 이용 코호트로 재분류할 수 있다.

반영: 실제 회원 ID·지표 버전별 최소 최초 시각과 조건별 known/unknown을 `product_member_first_usage`에 유지한다. 원본 90일/활동일 180일 만료로 요약을 재설정하지 않고 회원 계정 유지 기간에 별도 보존하는 제안이다. 확인 불가한 과거는 unknown으로 신규/최초 코호트에서 제외하며, 최초 요약이 있어도 미보존 재방문 날짜를 미재방문으로 판단하지 않는다. 버전 변경을 신규 이용으로 세지 않는다. 상세 기록 보존 기간은 유지하고 요약의 탈퇴 처리·최종 운영 보존은 구현 전 확정한다.

반영 검증은 문서의 계약·링크·표 구조·이전 정의 잔존 여부를 대상으로 한다. 앱·DB·PWA·운영 보존 설정 변경은 없다.
