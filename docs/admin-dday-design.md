# 관리자 디데이 기준일·표시 문구 관리 설계

작성일: 2026-10-04 KST. 상태: **관리자·일반 화면 UI 승인 / 전체 구현 / 운영 DB 적용 / v1.6.0 웹 릴리스**.

현재 구현 범위: `/admin/dday`의 조회·편집·미리보기·저장과 홈·로그인·회원가입의 공통 설정 표시를 연결했다. 사용자가 사용자용 문구 변경을 포함한 기능 개발을 승인했으며, 공통 문구·로딩·오류 안내·긴 문구 줄바꿈까지 적용했다. 브라우저와 사전 렌더링 진입점에 `ExamScheduleProvider`를 사용하고 초기 HTML에는 조회 중 상태만 출력한다. 격리 SQL/Vitest/모의 Playwright로 검증하며 사용자가 DB 적용·버전 관리·커밋·push를 명시적으로 요청하여 v1.6.0 릴리스를 진행한다. [운영 적용 기록](admin-dday-rollout.md)을 따른다. [분리 미리보기](previews/dday-public.html)도 운영 요청 없이 확인할 수 있다.

## 1. 목적과 현재 구현

관리자가 LEET 시험일과 공통 표시 문구를 수정하면 홈·로그인·회원가입에 같은 설정이 반영되어야 한다. 최초 기능 배포 이후 날짜·문구 변경에는 코드 수정이나 웹 재배포가 필요하지 않도록 한다.

요구 반영: 시험일 외에 문구도 수정할 수 있도록 **시험일 + 공통 표시 문구 템플릿**을 한 설정으로 관리한다. `{date}`는 시험일, `{dday}`는 자동 계산한 디데이로 치환한다. 예를 들어 `LEET 시험까지 {dday}`는 `LEET 시험까지 D-120`으로 표시된다. 관리자와 일반 화면 모두 승인된 개발 범위에 포함한다.

변경 전 `src/utils/dday.ts`의 `EXAM_DATE`는 `2026-07-19`로 고정되어 있었다. 구현 후에는 런타임 기본 날짜 없이 공개 설정의 시험일을 사용한다. `dday.ts`도 날짜·현재 시각을 인자로 받는 순수 계산 인터페이스다.

| 위치 | 변경 전 표시 | 구현 후 |
|---|---|---|
| `src/pages/HomePage.tsx` | `D-N`, `D-Day`, `D+N` | 같은 영역에서 공통 템플릿을 치환한 문구 표시 |
| `src/pages/LoginPage.tsx` | `YYYY.MM.DD 시험일 D-N` | 날짜·디데이·문구를 같은 조회 결과로 표시 |
| `src/pages/SignupPage.tsx` | 로그인과 같은 형식 | 홈·로그인과 같은 공통 문구 표시 |

변경 전에는 브라우저 로컬 시간대와 렌더링 시점으로 계산해 해외 시간대·열린 화면의 자정 갱신에 문제가 있었다. 구현은 한국 시간의 달력 날짜를 기준으로 계산하고 자정·포커스 복귀에 다시 갱신한다.

디데이 기준일은 홈의 채점 학년도 선택과 별개다. 시험일을 변경해도 `selectedYear`, 정답·환산표·기출문제·개인 이력·사설 시험일은 바뀌지 않는다. 다음 시험일을 추정하거나 매년 자동으로 전환하지 않는다.

## 2. 운영 DB 확인 결과

2026-10-04에 현재 앱의 프로젝트 식별자와 환경 변수의 프로젝트가 일치하는지 확인한 뒤 Supabase Management API의 `database/query/read-only`로 테이블 이름·RLS·관리자 함수 정의·마이그레이션 메타데이터를 조회했다. 회원 데이터나 성적은 조회하지 않았다.

- 조회한 `public`·`private` 테이블 목록에는 시험 일정·디데이 전용 설정 테이블이 없다. 아래 `exam_schedule`은 **이후 v1.6.0에서 운영에 적용한 신규 객체**다.
- 기존 `private.admin_roles`는 RLS가 활성화되어 있고 브라우저의 직접 접근이 차단되어 있다.
- `private.is_admin()`은 `auth.uid()`와 `role = 'admin'`을 검사한다. `moderator`는 이 권한을 얻지 않는다.
- `public.current_user_is_admin()`은 SECURITY INVOKER 함수이며 현재 사용자의 권한 확인에 사용한다.
- 공지 UPDATE 정책은 `USING`과 `WITH CHECK` 양쪽에서 기존 `private.is_admin()`을 호출한다. 신규 설정에도 같은 권한 기준을 적용한다.
- 원격 마이그레이션은 12개이고 최신은 `20261004050638_admin_dashboard_and_member_options`다. 공지·관리자 정책의 원격 버전 번호는 로컬 파일과 다르며 과거 원격 전용 이력도 존재한다. 구현 때 전체 `db push`로 이력을 맞추려 하지 않고 신규 마이그레이션 적용 범위를 별도로 확인한다.

## 3. 데이터 모델과 권한

`public.exam_schedule`에 서비스 전체가 사용하는 현재 시험일과 공통 문구 **한 행**을 저장한다. 화면별 템플릿·여러 학년도 일정·발행 예약·범용 JSON 설정은 첫 버전에 포함하지 않는다.

| 컬럼 | 타입·제약 | 의미 |
|---|---|---|
| `key` | `text`, PK, `CHECK (key = 'leet')` | 한 행만 허용하는 고정 키 |
| `exam_date` | `date`, NOT NULL | 실제 시험 시행일, API에서는 `YYYY-MM-DD` |
| `display_template` | `text`, NOT NULL, 아래 템플릿 검증 적용 | 세 화면에 함께 적용할 표시 문구 |
| `revision` | `integer`, NOT NULL, 초기 1, 양수 | 동시 수정과 응답 비교용 버전 |
| `updated_at` | `timestamptz`, NOT NULL | DB가 기록하는 마지막 변경 시각 |

날짜는 유한한 날짜이며 `2000-01-01`~`2099-12-31` 범위로 제한한다. 과거 날짜도 허용한다. 기존 `D+N` 동작과 잘못 저장한 날짜 복구에 필요하다. 프론트에서도 같은 유효 범위를 검사한다. 이 범위는 정답·기출 학년도 지원 범위와 무관하다.

마이그레이션은 현재 기준일 `2026-07-19`와 공통 초기 문구 `{date} 시험일 {dday}`로 한 행을 초기화한다. 이 문구는 로그인·회원가입의 현재 표시 형식을 유지하고, 홈에는 날짜와 `시험일` 문구가 추가된다. 세 화면을 하나의 공통 문구로 통일하면 현재의 서로 다른 표시 형식을 모두 보존할 수 없으므로 이 변화는 승인된 일반 화면 UI 범위에 포함한다. 다음 시험의 실제 날짜와 원하는 문구는 관리자가 확인하여 저장한다. 특정 미래 날짜를 가정해 시드하지 않는다.

권한 설계:

| 요청자 | SELECT | UPDATE | INSERT / DELETE |
|---|---|---|---|
| 비로그인 `anon` | 허용 | 차단 | 차단 |
| 일반 로그인 사용자 | 허용 | RLS로 차단 | 차단 |
| 기존 `admin` 역할 | 허용 | `exam_date`, `display_template`만 허용 | 차단 |

- RLS를 활성화하고 기본 권한을 회수한 뒤 `anon`·`authenticated`에 SELECT를 명시적으로 부여한다.
- `authenticated`에는 컬럼 단위 `UPDATE (exam_date, display_template)`만 부여한다. UPDATE 정책의 `USING`·`WITH CHECK` 모두 `(select private.is_admin())`을 검사한다.
- DB의 BEFORE UPDATE 트리거가 날짜 또는 템플릿이 실제로 변경될 때 `revision = OLD.revision + 1`, `updated_at = now()`를 설정한다. 두 값 모두 같으면 버전·수정 시각을 유지한다. 트리거는 SECURITY INVOKER와 고정된 `search_path`를 사용하며 새 관리자 권한 함수를 만들지 않는다.
- 브라우저가 키·버전·수정 시각을 직접 변경하거나 행을 추가·삭제할 수 없어야 한다. UPDATE 0행을 저장 성공으로 취급하지 않는다.
- 공개 테이블에는 수정자 UUID·이메일·내부 메모를 넣지 않는다. 첫 버전은 최종 수정 시각만 제공하며 별도 변경 감사 이력은 후속 범위다.

공지 관리와 같이 기존 브라우저 Supabase 클라이언트에서 직접 조회·수정한다. 새 Edge Function·service role 키·Storage·Realtime은 필요하지 않다. RLS와 grants를 함께 설계하는 근거는 [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security) 및 [Data API 권한 문서](https://supabase.com/docs/guides/api/securing-your-api)를 따른다.

## 4. 관리자 화면 구현

`/admin`에 **디데이 관리** 카드 하나를 추가하고 `/admin/dday`로 연결한다. 기존 `AdminRoute`와 `useAuth()`를 사용한다. 기존 공지·통계 메뉴는 유지한다.

```text
디데이 관리                              돌아가기
홈·로그인·회원가입에 표시할 LEET 시험일과 문구를 설정합니다.

현재 적용 중
시험일 2026.07.19   디데이 D+N   마지막 수정 YYYY.MM.DD HH:mm KST
현재 문구: {date} 시험일 {dday}

LEET 시험일  [ YYYY-MM-DD ▾ ]
한국 시간 기준으로 계산합니다.

표시 문구  [ LEET 시험까지 {dday}                    ]
{date}: 시험일 / {dday}: 디데이 · 세 화면에 같은 문구가 표시됩니다.

저장 후 표시 미리보기
홈                 LEET 시험까지 D+N
로그인             LEET 시험까지 D+N
회원가입           LEET 시험까지 D+N

[저장]  [변경 취소]
저장하면 세 화면에 적용됩니다.
```

위 `N`과 수정 시각은 구성 설명용 자리표시자다. 실제 미리보기는 입력한 날짜·템플릿과 현재 KST 날짜로 계산한다. 관리자는 시험명·학년도를 문구의 일반 텍스트로 입력할 수 있지만 별도 시험명·학년도 컬럼, 노출 토글·자동 전환 설정은 추가하지 않는다.

- 기존 `PageHeader`, 날짜 입력, 단일 행 텍스트 입력, 버튼, `admin.css`를 재사용하는 폼으로 구성한다. 모바일에서도 동일한 순서로 한 열에 표시한다.
- 날짜나 문구를 입력하면 미리보기만 바뀐다. 저장 전에는 서비스 설정이 바뀌지 않는다. 저장은 두 값을 하나의 UPDATE로 반영한다.
- 조회 중·조회 실패·저장 중·변경 없음·유효하지 않은 입력에서는 저장을 비활성화한다. 관리자 폼은 로컬 캐시만으로 편집을 허용하지 않고 최신 서버 조회에 성공해야 활성화한다.
- 저장 성공은 DB 응답에서 변경된 행을 확인한 후 표시한다. 성공한 응답으로 공통 캐시와 폼 기준값을 함께 갱신한다.
- 저장 실패 시 입력을 유지하고 한국어 오류를 표시한다. 변경 취소는 마지막으로 확인한 서버 값으로 폼을 되돌린다. 헤더 돌아가기·브라우저 뒤로가기/앞으로가기·새로고침/탭 닫기에는 미저장 변경 확인을 제공한다. BrowserRouter의 같은 문서 내 이동 취소는 원래 이력 위치로 복구해 폼 입력을 유지한다.
- 과거 날짜도 저장할 수 있지만 `지난 시험일입니다. {dday}는 D+N으로 표시됩니다.` 안내를 미리보기 옆에 제공한다.
- 관리자 권한 상실·계정 전환·로그아웃에서는 편집 상태를 제거하고 기존 접근 제한 흐름을 따른다. 이전 계정의 늦은 저장 응답을 새 계정의 성공으로 표시하지 않는다.

일반 화면은 기존 표시 영역·색상·서체와 치환 날짜 형식을 유지한다. 문구는 관리자가 설정한 내용으로 바뀌며 길이에 따라 영역 안에서 줄바꿈한다. 긴 단어도 화면 밖으로 넘치지 않도록 한다. 공통 초기 문구에 따른 홈의 날짜 추가, 관리자가 문구를 바꿨을 때의 본문 변화·줄바꿈, 비동기 로딩·조회 불가 상태를 승인된 UI 범위에 포함한다.

### 표시 문구 템플릿 규칙

| 입력 예시 | 표시 예시 |
|---|---|
| `{dday}` | `D-120` |
| `LEET 시험까지 {dday}` | `LEET 시험까지 D-120` |
| `{date} 시험일 {dday}` | `2026.07.19 시험일 D-120` |
| `2027학년도 LEET까지 {dday}` | `2027학년도 LEET까지 D-120` |

예시의 날짜·숫자·학년도는 형식을 설명하는 가상 조합이다. 학년도를 텍스트에 직접 넣으면 자동으로 변경되지 않으며 관리자가 날짜와 함께 확인한다.

- 지원 치환자는 대소문자를 구분하는 `{date}`와 `{dday}` 두 개다. `{date}`는 `YYYY.MM.DD`, `{dday}`는 기존 계산 결과로 치환한다. 같은 치환자가 여러 번 나오면 모두 치환한다.
- 일반 텍스트와 두 치환자만 허용한다. `{year}`, `{DDAY}`, 중첩·짝이 맞지 않는 중괄호 등은 잘못된 템플릿으로 보고 저장을 차단한다. 임의 중괄호의 이스케이프 문법은 첫 버전에 제공하지 않는다.
- 저장 전 앞뒤 공백을 제거하고 공백뿐인 문구는 허용하지 않는다. 템플릿은 Unicode 코드 포인트 기준 1~100자로 제한한다. 줄바꿈·탭·제어 문자는 허용하지 않는다. 서버의 유한 날짜·문구 제약과 프론트 검증을 일치시킨다.
- 두 치환자는 선택 사항이다. 일반 문구만 저장할 수도 있다. `{dday}`를 생략하면 `이 문구에는 자동 디데이가 표시되지 않습니다.` 안내를 제공하고 실제 미리보기에서도 숫자 디데이를 붙이지 않는다. `{date}`를 생략하면 날짜를 별도로 붙이지 않는다.
- HTML·Markdown·JavaScript를 실행하거나 해석하지 않고 React 텍스트로 표시한다. HTML처럼 생긴 텍스트도 그대로 문자로 보이며 링크·색상·글자 크기 편집은 제공하지 않는다.
- DB에서도 길이·공백·제어 문자·지원 치환자 구문을 검증해 브라우저 검증을 우회한 잘못된 문구를 차단한다. 조회·캐시를 읽을 때도 같은 규칙으로 응답을 검증한다.
- 미리보기와 실제 세 화면은 같은 치환 함수를 사용한다. 자정에는 저장된 템플릿의 `{dday}`만 다시 계산하며 DB에 완성된 표시 문자열을 저장하지 않는다.

## 5. 공통 조회·계산·실패 처리

`ExamScheduleProvider`와 `useExamSchedule()`을 인증 상태와 분리된 **공개 설정 상태**로 추가한다. 인증 원본은 기존 `AuthContext`만 유지한다. Provider는 브라우저와 사전 렌더링 양쪽 진입점에서 사용하되 사전 렌더링은 초기 일정 없는 상태로 렌더링한다.

`useDday()`는 공통 설정과 현재 시각을 받아 `examDate`, `dday`, `ddayText`, 템플릿을 치환한 `displayText`, 조회 상태를 한 번에 반환한다. 세 페이지는 `displayText`를 그대로 사용하고 각각 날짜·고정 문구를 다시 붙이거나 `calculateDday()`·`getDdayText()`를 별도로 호출하지 않는다. `src/utils/dday.ts`는 날짜와 현재 시각을 인자로 받는 순수 계산 함수로 바꾸고 하드코딩된 런타임 기본 날짜는 제거한다. 템플릿 검증·치환은 별도 순수 함수로 분리한다.

계산 규칙:

1. `YYYY-MM-DD`를 연·월·일로 검증하여 읽는다. 브라우저 로컬 시간의 `new Date('YYYY-MM-DD')`·`setHours()` 조합을 사용하지 않는다.
2. 현재 시각에서 `Asia/Seoul`의 연·월·일을 구한다.
3. 양쪽 달력 날짜를 UTC 날짜 번호로 변환해 차이를 계산한다. 실제 시간 간격을 올림하여 날짜 차이로 해석하지 않는다.
4. 미래는 `D-N`, 당일은 `D-Day`, 과거는 `D+N`을 유지한다.
5. 다음 KST 자정에 다시 계산하고, 탭이 다시 보이거나 포커스를 얻으면 즉시 현재 날짜를 재계산한다. 타이머는 정리하여 중복 실행을 막는다.

조회·반영 규칙:

- 앱의 디데이 표시 화면 진입 시 조회한다. 동시에 발생한 요청은 하나로 합치고 세 화면은 동일한 메모리 결과를 공유한다.
- 디데이를 표시하는 화면이 활성·visible인 동안 60초 주기로 한 번 재조회한다. 숨김 탭에서는 폴링을 중단한다. 화면 재진입·포커스·온라인 복귀 시 갱신하며 겹친 요청은 합친다.
- 관리자 저장 성공 시 현재 앱에는 응답으로 즉시 반영한다. 다른 열린 탭은 storage 이벤트로 재조회를 요청한다. 다른 사용자의 열린 화면에는 정상 네트워크에서 다음 60초 조회 때 반영되며 숨김 화면은 복귀 때 반영된다. 실시간 즉시 전달을 보장하지 않는다.
- 공개 기준일·템플릿·버전·수정 시각·조회 시각만 프로젝트별 localStorage 키에 저장할 수 있다. 서버 응답을 검증한 값만 기록하며 저장소 접근 실패는 앱을 막지 않는다. 템플릿 없는 이전 형식 캐시는 무시한다. 계산된 디데이·완성된 표시 문자열은 저장하지 않고 매번 계산·치환한다.
- 캐시는 마지막 확인한 값으로 초기 표시·일시 장애를 완화하는 용도다. 최초 서버 조회는 캐시 유무와 무관하게 수행한다. 검증된 서버 응답이 캐시보다 우선하고 손상된 캐시는 무시한다.
- 오래 걸린 이전 조회가 관리자 저장 응답이나 최신 조회를 덮어쓰지 않도록 요청 세대와 서버 버전을 검사한다. 다른 탭의 캐시 이벤트는 서버 재조회 신호로만 사용한다.

| 상태 | 일반 화면 동작 | 관리자 화면 동작 |
|---|---|---|
| 유효한 마지막 조회 값 있음 | 같은 응답의 날짜·문구로 표시하며 서버 갱신 | 최신 서버 조회 전까지 편집·저장 잠금 |
| 최초 조회 중, 캐시 없음 | 기존 영역에 `불러오는 중…` | 조회 상태 표시, 저장 잠금 |
| 조회 실패, 캐시 있음 | 마지막 확인한 날짜·문구를 유지하고 `마지막 확인한 설정 기준` 안내·콘솔 기록 | 오류·다시 불러오기, 입력 보존·저장 잠금 |
| 조회 실패, 캐시 없음 | 기존 영역에 `디데이 설정을 불러오지 못했습니다.` | 오류·다시 불러오기, 저장 잠금 |
| 행 없음·잘못된 응답 | 캐시가 있으면 유지, 없으면 조회 실패와 동일 | 설정 오류 안내, 서버 행 초기화 필요 |

조회 실패가 채점·로그인·회원가입 등 기존 기능 실행을 막지 않게 한다. 마지막 조회 값이 있는 장애 상황에서는 이전 기준일·문구가 표시될 수 있다. 날짜와 문구는 한 응답·같은 버전의 설정으로만 사용하고 신규 날짜에 이전 문구를 섞지 않는다. 현재 값의 강한 실시간 일관성을 요구하는 기능으로 설계하지 않는다.

## 6. 저장과 동시 수정

저장 요청은 정규화·검증한 `exam_date`, `display_template`를 하나의 UPDATE로 변경하고 `key = 'leet'` 및 **폼을 조회했을 때의 revision**을 조건으로 사용한다. 날짜만 또는 문구만 수정했어도 두 필드를 같은 설정으로 보낸다. 응답에서 다섯 컬럼을 다시 조회한다.

- 변경된 행이 한 개이고 예상 날짜·템플릿·증가한 버전이 확인되면 저장 성공이다. 문구만 변경한 경우도 버전이 증가해야 한다.
- 0행이면 공개 행과 현재 관리자 권한을 다시 읽어 충돌·권한 상실·설정 누락을 구분한다. 충돌 시 `다른 관리자가 디데이 설정을 변경했습니다. 최신 값을 확인해주세요.`와 최신 서버 날짜·문구를 보여 주고 두 입력값은 보존한다. 최신 값을 확인하기 전 재저장을 막고 자동 덮어쓰기는 하지 않는다. 관리자 A의 날짜 변경과 관리자 B의 문구 변경도 같은 버전에 대한 충돌로 처리한다.
- 네트워크 오류·타임아웃은 저장됐는지 모르는 상태일 수 있다. 자동 재시도하지 않고 읽기 전용 재조회로 현재 날짜·템플릿·버전을 확인한다. 두 값이 모두 일치하면 `현재 서버에는 이 날짜와 문구가 적용되어 있습니다.`로 안내한다. 하나라도 다르면 적용 확인으로 취급하지 않는다. 누가 저장했는지 또는 이번 요청이 성공했는지는 감사 이력 없이 단정하지 않는다.
- 읽기 확인도 실패하면 입력을 유지하고 저장 상태 확인·다시 불러오기 동선을 제공한다. 기준 버전을 확인한 뒤에만 새로운 저장 시도를 허용한다.

## 7. 홈 초기 HTML과 재배포 없는 변경

`scripts/prerender.ts`는 외부 fetch를 금지한 채 `src/entry-prerender.tsx`의 실제 홈 UI를 HTML로 저장한다. 여기에 DB 날짜·문구를 빌드 시 복사하면 관리자 수정 후에도 이전 설정이 초기 HTML에 남는다.

사전 렌더링의 디데이 영역에 **최초 조회 중 상태**를 출력하고 날짜·숫자 디데이·관리자 설정 문구는 넣지 않는 것이다. 나머지 홈 본문·메타데이터·레이아웃은 유지한다. 브라우저 앱 시작 후 캐시 또는 공개 DB 조회의 같은 날짜·문구 설정으로 표시한다. 빌드 중 운영 DB 접근이나 Vercel 재배포 트리거는 추가하지 않는다.

이에 따라 JavaScript 없는 홈에서는 디데이 값·관리자 설정 문구가 제공되지 않는다. 관리자가 바꾼 날짜·문구를 최초 HTML부터 제공하는 요구가 추가된다면 서버 렌더링·동적 HTML 제공을 별도 설계해야 한다. 이 첫 버전의 범위에는 포함하지 않는다.

## 9. 검증 및 적용 순서

필수 인수 기준:

1. 기준일 하루 전·당일·하루 후, 월말·연말·윤일 및 KST 자정 직전·직후를 검사한다. 한국·UTC·미국 시간대에서도 같은 현재 시각이면 결과가 같아야 한다.
2. 세 페이지의 날짜·디데이·치환 문구가 일치하고 자정·백그라운드 복귀·날짜 또는 문구 변경 후 갱신된다. `{date}`·`{dday}`의 반복·생략, 일반 문구만 입력, 공백·최대 길이·알 수 없는 치환자·잘못된 중괄호·제어 문자·HTML처럼 생긴 텍스트를 검사한다. 채점 학년도와 개인 이력은 변하지 않는다.
3. 조회 실패·행 없음·손상 캐시·localStorage 접근 실패에서도 주요 사용자 기능을 사용할 수 있다. 요청 중복·늦은 응답·타이머 해제를 검사한다.
4. 격리 SQL 테스트에서 anon/일반 사용자/moderator의 쓰기 차단, admin의 날짜·문구 변경, 문구만 바꾼 경우의 버전 증가, 동일 값 저장 시 버전 유지, 권한 회수, 키·버전·시각 직접 변경 및 INSERT/DELETE 차단, 유효하지 않은 날짜·문구와 동시 수정 충돌을 확인한다.
5. 모의 Supabase Playwright에서 관리자 메뉴·직접 URL 접근·폼 입력·미리보기·유효성 검사·저장 성공/실패·충돌·응답 미확인·계정 전환을 검사한다. 모든 쓰기는 모의 서버에만 발생해야 한다.
6. 데스크톱·모바일의 세 화면 표시 영역·스타일 및 관리자 한 열 폼을 검사한다. 긴 문구·긴 단어·토큰 반복의 치환 결과에 가로 넘침이 없어야 한다. 사전 HTML에 하드코딩된 기준일·숫자 디데이·관리자 설정 문구가 없고 JS 앱 시작 후에는 공개 조회 값이 반영되는지 확인한다.
7. `npm run check`를 통과하고 build 산출물 변경을 확인한다. 기존 사전 렌더링·화면 테스트의 모의 응답도 신규 공개 조회에 맞게 갱신한다.

적용 순서는 **구체적인 UI 변경안 승인 → 로컬 구현과 격리 검증 → 운영 DB 적용 및 웹 배포 명시 요청 확인 → 신규 DB 구조·초기 행 적용 → 공개 읽기·권한 차단 확인 → 웹 배포**다. 기존 앱은 신규 테이블을 사용하지 않으므로 DB를 먼저 준비할 수 있다. 웹 버전 준비는 기존 버전 관리 규칙을 따른다.

운영에서는 공개 SELECT와 실제 grants·RLS를 먼저 읽기 전용으로 검사한다. 운영 날짜·문구 저장을 통한 쓰기 검증은 운영자 본인의 의도적 변경이나 별도 승인된 테스트 데이터에만 수행한다. 개발용 로컬 화면에서 운영 저장을 클릭하지 않는다.
