# 관리자 통계·PWA·변화 대시보드 통합 재검토

검토일/설계 반영일: 2026-10-04 KST. 상태: **설계 본문·API 계약·인수 기준 반영 완료 / 앱·미리보기 미반영 / 운영 미적용**.

대상: [전체 통계 설계](admin-analytics-design.md), [PWA 설계](admin-pwa-analytics-design.md), [변화 대시보드 설계](admin-dashboard-design.md), [현재 구현·운영](admin-analytics.md), 분리된 예시 HTML 및 관련 클라이언트 코드. 이전 [검토 기록](admin-analytics-review.md)은 당시 반영 이력으로 유지한다.

결론: 서비스 이용·채점·PWA·실제 회원 활동을 분석하고 대시보드에서 변화를 발견하는 구성은 적절하다. 범위 확대나 구조 재설계는 필요하지 않다. **시간 구간/그래프 표현 두 항목, 주요 변화 선정, 인증·권한 오류 처리의 네 항목**은 구체적인 보완이 필요하다.

## 설계 반영 결과

사용자의 반영 요청에 따라 아래 기준을 확정해 설계 본문에 통합했다. 이후 1~4장은 검토 당시의 문제와 대안을 보존한 기록이며 행 번호도 **수정 전 문서 기준**이다. 현재 구현 목표는 아래 확정 기준을 따른다.

| 항목 | 확정 기준 | 반영 위치 |
|---|---|---|
| 길이가 다른 집계 구간 | 곡선은 일별 고유 수/채점 수의 합 ÷ 구간 전체 완료 일수. 가용한 0건 일자 포함, 하나라도 미가용/미완료이면 null. 짧지만 완전 가용한 마지막 구간은 실제 일수로 나눠 연결. 카드/툴팁의 기간·구간 DISTINCT는 별도 유지 | [대시보드](admin-dashboard-design.md) 2·3·7·8·9장, 전체/PWA 설계 |
| 윤년 경계 | 원래 시작일에서 1~11개월 이동한 경계와 실제 종료일로 정확히 12구간. 이전 구간은 같은 일자 오프셋과 일수 | 대시보드 7·9장 |
| 주요 변화 누락 | 정책 버전 2: 충분한 표본의 채점 관측률 감소 → 건수 감소 → 관측률 증가 → 건수 증가. 순위 안에서 정의된 점수·고정 키로 선정, 범주별 1개/전체 3개 | 대시보드 4·8·9장, 전체/PWA 인수 기준 |
| 권한 거절 뒤 자료 유지 | 안전한 상태/코드의 오류 분류. 일시 오류만 이전값 유지. 현재 계정/인가 세대의 401/403은 모든 관리자 자료 제거·추가 조회 중단·세대 증가로 늦은 성공 차단 | 대시보드 7·8·9장, [전체](admin-analytics-design.md) 7·8·10장, [PWA](admin-pwa-analytics-design.md) 7·8장 |

일평균은 추이의 표현 변경이며 카드의 기간 고유 수·실제 회원 식별·PWA 실행 정의는 유지한다. 자료 누락일만 빼고 평균을 계산하는 대안과 마지막 짧은 구간의 합계를 따로 점으로 표시하는 대안은 채택하지 않았다. 선정 기준은 변화 발견을 위한 운영 정책이며 감소를 장애로 단정하지 않는다. 신규 기능이나 추가 이벤트 수집은 이번 보완 범위에 포함하지 않는다.

## 1. 서로 다른 일수의 합계를 한 곡선으로 연결하면 변화가 과장된다

근거: 대시보드 설계 154~161행. 6개월은 시작일부터 7일씩 집계하며 마지막 남은 일수도 같은 곡선에 포함한다. 구간별 고유 수·횟수를 Y축에 그대로 사용하고 일수는 툴팁에만 표시한다.

재현:

- 2026-04-04~10-03은 183일이다. 마지막 두 구간은 9/26~10/2의 **7일**, 10/3의 **1일**이다.
- 매일 채점 10회로 실제 이용이 일정해도 마지막 합계는 `70 → 10`이므로 곡선에 약 **85.7% 감소**가 생긴다.
- 현 가상 미리보기의 채점 값도 마지막 두 점이 `138 → 20`이다. 이는 실서비스 기록이 아니라 예시 데이터·구간 계산의 재현이다.
- 1년의 월간 합계도 28·29·30·31일 차이로 흔들릴 수 있다. 단조 보간은 선의 과도한 굴곡을 막지만 합계의 기간 차이를 보정하지 않는다.

권장 보완:

- 일/주/월 범위 선택과 곡선 표현은 유지한다.
- 일반 추이의 기본 곡선은 **구간 내 일평균 DAU·일평균 활성 세션·일평균 채점 횟수**처럼 일수 차이에 영향을 덜 받는 값으로 통일하고 단위에 `일평균`을 표시한다. 현재·이전 대응 구간에도 같은 계산을 적용한다.
- 기간 전체 카드와 툴팁/표의 주간·월간 고유 회원·세션·정확한 총횟수는 계속 별도로 제공한다. 일평균 DAU를 주간/월간 고유 회원으로 이름 붙이지 않는다. 이 변경에는 기존 '주간·월간 고유 수 곡선' 정의의 명시적 수정이 필요하다.
- 평균은 조회 가능한 **완료 일자**만으로 계산하되 자료 누락일을 조용히 분모에서 빼고 완전 자료처럼 표시하지 않는다. 선택 구간이 부분이면 부분 상태·실제 일수·비교 불가를 유지한다.
- 주간 고유 수 곡선을 계속 제공하는 대안은 마지막 짧은 구간을 완전한 7일 점과 연결하지 않고 별도 점·짧은 구간 안내로 표시하는 것이다. 총합·고유 수와 평균 표현을 한 지표 이름으로 섞지 않는다.

검증 기준: 일정한 일별 이용의 마지막 1일 때문에 기본 추이 곡선에 85.7% 급감이 생기지 않는다. 부분 구간과 정상 0건을 구분하고 카드 기간 DISTINCT를 보존한다.

## 2. 윤년 경계에서 월간 12개 구간 계약이 깨질 수 있다

근거: 대시보드 설계 148~155행 및 미리보기 `shiftMonths`/`period` 함수.

재현: 예시 종료 경계를 `2024-02-29 00:00`로 바꾸면 1년 시작 경계는 월말 보정으로 `2023-02-28`이다. 시작점에 12개월을 더하면 `2024-02-28`까지이므로 현재 반복 규칙은 마지막 하루를 더해 **13개 구간**을 만든다. 설계의 '12개 구간'과 다르다.

권장 보완: 월간 경계 배열을 시작점 + 1~11개월, 실제 선택 종료 경계로 명시하여 **12개 구간**을 만든다. 월말 보정은 원래 시작 날짜 기준으로 계산하고 마지막 경계를 다시 추정하지 않는다. 이전 곡선은 이 실제 구간의 일자 오프셋으로 같은 일수의 대응 구간을 만든다.

검증 기준: 2/29·2/28·월말 30/31일·윤년 전후의 1년 범위에서 첫 경계/마지막 경계·365/366일·12개 구간·중복/누락 없음이 일치한다. 기존 48가지 화면 전환 확인은 기준일 2026-10-04였으며 이 경계 검증을 포함하지 않았다.

## 3. 주요 변화의 고정 범주 순서가 중요한 감소를 숨길 수 있다

근거: 대시보드 설계 92행. 최대 3개를 이용량 → 기능 → PWA → 채점 순서로 고른다.

문제: 앞의 세 범주에서 후보가 하나씩 있으면 채점 관측률은 항상 네 번째다. 예를 들어 충분한 표본에서 `72% → 40%`로 크게 떨어져도 회원·기출·PWA 증가만 상단에 나타날 수 있다. '한눈에 확인할 변화'라는 목적에 맞지 않는다. 상세 표에 존재하는 것만으로 상단 누락이 해결되지는 않는다.

권장 보완:

- 가용 자료·표본 기준과 범주별 최대 1개·전체 최대 3개 원칙은 유지한다.
- 선정 전에 **확인할 감소/문제**와 일반 증감을 구분한다. 충분한 표본에서 기준을 넘는 채점 관측률 감소는 앞쪽에 최소 한 자리를 확보한 뒤 나머지를 선택한다. 확정 저장 실패의 악화 등을 포함하려면 먼저 분자/분모·지원 상태를 정의한다.
- 감소를 서버 장애·사용자의 의도적 포기로 단정하지 않는다. 문구는 '관측률 감소, 흐름 확인 필요'처럼 관측 근거만 표현한다.
- 건수와 %p를 직접 같은 숫자로 정렬하지 않는다. 우선순위 정책은 고정 키/버전으로 관리하고 판정 가능한 지표만 후보에 포함한다.

검증 기준: 회원·기능·PWA 증가와 충분한 표본의 채점 관측률 급락이 동시에 있으면 상단에서 급락을 확인할 수 있다. 비교 불가·미성숙·소표본을 문제로 과장하지 않는다.

## 4. 이전 자료 유지 규칙에서 인증·권한 거절은 예외로 처리해야 한다

근거: 대시보드 설계 143~144행. 같은 계정·필터라면 갱신 실패 시 이전 자료를 유지할 수 있으나 실패 종류에 따른 예외는 정의되어 있지 않다. 현재 `adminAnalyticsApi.ts`는 오류를 일반 Error/한국어 문구로 반환하며 HTTP 상태/안전한 코드의 구조화된 전달이 없다. 회원 목록·활동·감사 목록의 다음 페이지 실패도 오류 안내만 추가하고 이미 받은 data를 유지하는 분기가 있다.

문제: 서버가 `401` 또는 `403 ADMIN_REQUIRED`를 반환한 시점은 단순 네트워크 실패와 다르다. 이때 이전 회원 식별 정보와 활동을 계속 표시하도록 구현하면 역할 회수를 서버에서 확인하고도 화면에는 남을 수 있다. 이는 이미 제공된 데이터를 소급 회수할 수 있다는 뜻이나 서버 인가 우회가 확인됐다는 뜻은 아니다. **새로 인지한 인증/권한 거절 뒤 화면 유지 규칙**의 문제다.

권장 보완:

- 이전 조회 시각을 붙인 자료 유지는 통신 오류·서버 5xx 등 일시 실패로 제한한다.
- 명확한 인증·권한 거절, 로그아웃·계정 변경에는 개인 자료와 선택 회원·페이지 커서·계정별 메모리 결과를 비우고 추가 조회를 중단한다. 세션 재확인/기존 관리자 라우트 안내로 연결한다.
- API 오류는 안전한 `code`, HTTP `status`, 재시도 가능 여부를 보존하는 타입으로 반환한다. 한국어 문구 문자열을 비교해 권한 거절을 판정하지 않는다.
- 집계와 피드를 독립적으로 표시하는 일반 부분 실패와 달리 같은 관리자 세션의 권한 거절은 전체 관리자 자료 상태에 반영한다. 새로운 자동 폴링은 필요하지 않다.

검증 기준: 회원 목록/피드를 성공적으로 조회한 뒤 다음 요청에서 403을 받으면 기존 개인 행이 남지 않는다. 401·계정 변경도 구분하고, 일시적인 503에는 같은 계정/필터의 이전 결과와 실제 조회 시각을 유지할 수 있다. 정상 서버의 관리자 인가·역할 회수 테스트도 기존대로 수행한다.

## 유지할 설계와 운영 전 확정 사항

유지할 사항:

- 실제 회원 UUID 연결과 현재 이름/이메일 조회, 익명 기록 소급 연결 금지.
- PWA 실행·설치 안내·설치 이벤트를 구분하고 채널 교집합을 다시 DISTINCT하는 방식. 관측 신호의 의미는 [MDN display-mode](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/display-mode)와 [web.dev PWA 관측](https://web.dev/learn/pwa/detection)을 재확인했다.
- 관찰 종료/진행/유예/미확정 구분, 입력/실행 연결, 계산과 저장 응답 분리.
- 수집 전·중단·미지원·가용 0건의 구분, 같은 정의/필터/길이의 기간 비교.
- 1년/직전 1년을 위한 25개월 장기 사실 자료 제안과 90일 상세 활동의 분리. 일별 고유 수의 합으로 장기 고유 수를 만들지 않는 원칙.
- 기존 Edge 인가·SQL 재검사·개인 조회 감사·서버 전용 권한.

보존/탈퇴·역할/제외 계정 변경에 따른 과거 처리, 장기 발행 주기/실패 복구, 실제 PWA 기기·격리된 Supabase 권한 검증은 이미 문서에 남아 있는 운영 전 확정 사항이다. 새로운 누락이나 추가 기능 추천으로 중복 계산하지 않는다. [Vercel Analytics API 공식 문서](https://vercel.com/docs/analytics/web-analytics-api)도 확인했으며 현재 미연결 상태와 자체 통계와 모수를 분리하는 방향을 유지한다.

## 검증 범위

전체 설계·PWA·대시보드·구현 문서를 대조하고, 미리보기의 날짜/집계 계산만 Node VM에서 실행하여 6개월 마지막 7일/1일 값과 윤년 13개 구간을 재현했다. 클라이언트의 오류 분류·자료 유지 분기를 읽기 전용으로 확인했다. 운영 권한을 바꾸거나 실제 회원 자료를 조회하지 않았다. 이번에는 전체 앱 회귀/화면/원격 DB 검증을 새로 실행하지 않았다.

최초 검토 때에는 결과만 기록했으며, 후속 요청으로 위 네 기준을 설계 본문·API·인수 기준에 반영했다. 합성 계산으로 1999~2030년 11,688개 종료 날짜의 12구간·365/366일·같은 일수 비교와 일정 이용/가용 0건/누락의 평균, 주요 변화 임계값·우선순위·동률을 확인했다. 관련 문서 6개의 로컬 링크 43개·형식 및 `git diff --check`를 검사했다. 앱의 권한 거절 처리와 미리보기의 새 그래프/기간/선정 규칙은 아직 구현 검증하지 않았다. 앱·미리보기·DB·수집·배포·push는 이번에 변경하지 않았다. 실제 개발 때는 위 재현과 세대별 늦은 응답 차단을 회귀 검증에 포함한다. 문서 단위 커밋을 권장하며 main push는 실서비스 배포를 유발하므로 별도 요청 후 진행한다.
