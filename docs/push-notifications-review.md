## 1. 최초 검토의 결론과 경계

관리자 작성 → private 영속 대기열 → 서버 발송 → 기존 서비스 워커의 구조는 현재 정적 Vite 앱에 맞는다. 익명 구독과 회원 연결을 분리한 점, 접수와 실제 도착을 구분한 점, 불명확한 전송을 자동 재발송하지 않는 점, 최초 동의 이후 별도 회원 알림 설정을 두지 않는 제품 범위는 유지할 만하다.

다만 **발송 대상의 확인 규칙·익명 등록의 경쟁·계정 연결의 변경 순서·대량 처리 방식**을 현재 표현 그대로 구현해서는 안 된다. 아래 P1은 구현 전에 구체적인 계약과 검증을 추가해야 할 사항이다. P2는 첫 운영 적용 전에 마무리할 사항이다. 구현 코드의 취약점을 발견했다는 의미가 아니라 미구현 설계의 공백·회귀 위험을 검토한 결과다.

사용자가 확정한 범위는 전체 구독자(비로그인 포함)·전체 회원·선택 회원·본인 현재 기기 테스트, 수동 작성, 앱 내부 이동 주소, 최초 동의, 별도 수신 설정 없음이다. 예약·공지 가져오기·댓글 자동 알림을 다시 제안 범위에 넣지 않는다. 아래 선택 기능은 권고이며 채택 또는 UI 변경 승인을 받은 것으로 처리하지 않는다.

설계 문서·실제 AuthContext·SW·manifest·관리자 인증과 기존 migration의 계정 보관 경계를 대조했다. 운영 DB 메타데이터의 최신 상태는 이전 조사에서 DNS 실패로 확인하지 못했고 이번 검토도 그 제한을 유지한다. 실제 provider·회원·구독 대상으로 테스트하지 않았다. 공식 Web Push RFC, Supabase Auth/함수 제한, MDN API 문서로 플랫폼 사실을 확인했다.

### 2.1. 대상 변경 때문에 발송을 반복 실패시키지 않기

현 설계 6절은 대상 fingerprint가 바뀌면 409다. 예를 들어 126개 구독을 확인하는 동안 1명이 동의 철회하면 125개에 안전하게 보낼 수 있지만 현재 계약은 전체를 다시 확인해야 한다. 신규 구독·회원 연결 갱신이 잦으면 확인이 계속 무효화될 수 있다.

추천은 **확인한 대상 집합을 고정하고, 최종 접수 시 제외할 대상만 줄이는 방식**이다. 제목·본문·주소·대상 종류·선택 회원이 바뀌면 재확인한다. 구독 철회·만료·계정 연결 변화로 빠진 대상은 재확인 없이 제외하고 줄어든 건수를 접수 응답과 이력에 표시한다. 확인 이후 신규 구독자를 추가하지 않는다.

구체화 방법은 private 미리보기 스냅샷에 후보 subscription ID·구독/연결 세대를 짧게 보관하는 방법을 우선 검토한다. 이는 기존 `preview는 읽기만 한다`는 기술 선택의 변경이므로 본 설계에 바로 확정하지 않았다. 미리보기는 dispatch되지 않는 준비 상태이며 만료를 논리적으로 처리하고 실제 삭제는 보존 정책에 따라 별도로 정한다. 원래의 읽기 전용 방식을 유지하려면 immutable 자격 시각/세대를 사용한 cutoff 규칙을 별도로 증명해야 한다. 단순히 현재 건수가 원래 이하라는 조건만 쓰면 구독자가 바뀌어도 같은 숫자이므로 안전하지 않다.

검증: 126→125 철회 시 정상 접수, 신규 추가 시 확인 집합에 포함하지 않음, 같은 126개라도 사용자/기기가 교체되면 무단 추가 없음, 선택 회원 변경 시 재확인, 만료 preview 거절, 0개가 되면 실제 캠페인 발송 없음.

### 2.2. 미확인 등록이 정상 구독을 선점하지 않게 하기

현 설계의 endpoint_hash UNIQUE는 pending에도 적용된다. 공격자가 다른 기기의 endpoint와 구독 JSON 자료를 먼저 제출하면 등록 확인 nonce를 읽지 못해 active로 승격되지는 않지만, UNIQUE 때문에 실제 기기의 등록이 충돌할 수 있다. 이 문제는 소유 확인 challenge를 없애서 해결할 수 없다.

추천: pending 신청은 `(installation_id, endpoint_hash, request_id)`의 멱등성으로 관리하고, **검증된 활성 소유권에만 endpoint 유일성**을 강제한다. SW는 payload의 installation ID·구독 세대·endpoint/키 fingerprint를 자신의 IndexedDB와 실제 `getSubscription()` 결과에 비교한 뒤 확인한다. payload가 지정한 설치 ID를 그대로 신뢰하거나 다른 설치의 확인을 대신 수행하지 않는다.

확인 API는 challenge·소유 비밀·세대를 원자적으로 검사한다. 재전송 때 새 nonce로 이전 요청을 무작정 무효화하지 않고, 유효한 동일 challenge를 재사용하거나 명시적 challenge 세대로 처리한다. 이미 성공한 확인의 응답이 유실되면 동일 요청 재전송에서 성공 상태를 돌려준다. 등록 확인 전송도 영속 작업으로 기록해야 register 함수가 중간 종료된 뒤 재개할 수 있다.

설치 비밀 유실 후 재등록/같은 endpoint 재사용도 실기기 검증 대상으로 둔다. unsubscribe 후 반드시 새로운 문자열 endpoint가 나온다고 가정하지 않는다. 다른 설치로의 교체는 새 등록을 시작한 실제 SW의 수신 증명 이후에만 수행하고 옛 capability·회원 연결을 무효화한다. 익명 요청자의 `state`는 소유 증명한 자기 설치만 반환하며 endpoint 존재 여부 조회 API가 되지 않도록 한다.

검증: 타 설치의 pending 선점에도 정상 등록 가능, 동시에 등록해도 활성 소유권 하나, challenge ACK 중복/응답 유실, 재전송 순서 역전, 설치 저장소 유실·동일 endpoint 재사용, 만료 pending 재시도. 미확인 신청 수·endpoint별 확인 전송 횟수·전역 등록 비용 제한을 함께 확인한다.

### 2.3. 늦은 로그아웃이 새 계정 연결을 지우지 않게 하기

현재는 서버 발송 때 binding_revision을 검사하지만 bind/detach 요청 자체의 예상 revision 조건이 없다. `A detach가 느리게 진행 → B bind 완료 → A detach 도착` 순서에서는 B의 연결이 해제될 수 있다. 같은 회원의 토큰 갱신·페이지 재진입마다 bind가 revision을 올리면 발송 대기 작업이 불필요하게 제외된다.

추천: bind/detach/sync 변경에는 `expected_installation_revision`, `expected_binding_revision`, `request_id`와 현재 인증 문맥을 사용한다. 동일 userId·sessionId·구독 세대의 bind는 멱등 조회로 처리하며 revision을 올리지 않는다. 실제 연결 변경만 증가한다. detach는 예상 연결을 확인하고 다른 계정의 새 연결을 지우지 않는다. 409 이후 오래된 요청을 새 revision으로 자동 재실행하지 않는다.

클라이언트도 최신 AuthContext와 실제 세션을 요청 직전·응답 반영 전에 확인하고, 다른 탭·계정 변경에 대해 이전 요청 결과를 버린다. 설치 작업은 IndexedDB의 단일 변경 순서 또는 지원되는 브라우저 잠금+대체 경로로 직렬화한다. 프론트 세대 검사만으로 서버 쓰기를 되돌릴 수 있다고 설명하지 않는다.

로그아웃 후 익명 구독 유지라는 제안은 유지하되, 회원 탈퇴/정지는 익명 대상 강등과 구분한다. 단순 `auth.sessions` 행 존재 확인은 로그아웃 감지에는 유용하지만 time-box/inactivity 정책의 만료 판정을 완전히 대신하지 않는다. 현재 운영 Auth 정책에 맞는 session validity 계약을 먼저 확인한다. [Supabase 세션 만료·정리 규칙](https://supabase.com/docs/guides/auth/sessions)

검증: A detach/B bind 응답 순서 역전, 같은 회원 token refresh, 두 탭에서 bind, session 종료 후 남은 JWT, soft/hard 탈퇴, session time-box/inactivity 경계.

### 2.4. batch 크기와 전체 처리 시간을 함께 정하기

현 설계의 batch 20·동시 전송 5·timeout 5초·작업 예산 20초는 timeout이 꽉 찬 경우 `ceil(20/5)×5=20초`로 DB 처리와 결과 기록 여유가 없다. 1분 Cron 호출당 한 batch만 처리하는 방식으로 구현되면 10,000개는 `10,000/20=500분`, 약 8시간 20분이다. **이는 문서가 허용하는 느린 구현 예시이며 실제 성능 측정값이 아니다.**

추천: worker는 안전 마감 시각 전까지 여러 작은 batch를 반복하되, 새 외부 요청의 최악 timeout+결과 기록 여유가 남을 때만 시작한다. 남은 작업에는 DB에 저장한 다음 기동 의도를 남긴다. Cron은 잃어버린 기동을 복구하고, 지속 처리 방식에는 전역 worker slot lease·provider별 동시성/속도 한도·캠페인 간 공정성을 둔다. 자기 Edge 함수를 무제한 재귀 호출하지 않는다. pg_cron의 초 단위 실행은 upstream에서 지원하지만 실제 운영 확장 버전과 허용 실행을 확인한 뒤 선택한다. [pg_cron 공식 저장소](https://github.com/citusdata/pg_cron)

처리 목표는 작은 표본 평균으로 약속하지 않는다. 1,000개/10,000개, 느린 provider·429·중단·재시도를 포함한 총 완료 시간·p95·CPU·DB 시간을 측정한다. 제안 초기 제품 목표는 정상 provider에서 1,000개를 5분 이내 처리하는 것이며, 승인된 보장이나 검증된 수치는 아니다. 10,000개 상한은 벤치마크 전까지 지원 규모로 광고하지 않는다.

Supabase 문서상 요청당 CPU 제한은 2초이고 외부 I/O 대기와 구분된다. payload 암호화·DB JSON 처리 때문에 wall-clock 예산만 맞춰도 충분하지 않을 수 있다. 런타임과 실제 선택 라이브러리에서 측정한다. [Edge Function 제한](https://supabase.com/docs/guides/functions/limits)

### 2.5. 익명 등록 transport를 로그인 API와 분리하기

설계는 익명 호출의 Authorization을 비우고 무효 JWT는 401로 처리한다. 그런데 기존 Supabase SDK 호출을 그대로 재사용하면 설치된 SDK/키 유형에 따라 anon 키를 Bearer로 보내는 경로가 생길 수 있다. 이를 user JWT로 검사하면 모든 비로그인 등록이 실패한다.

추천: 익명 register/state/verify/detach에는 해당 경로의 전용 fetch transport를 명시한다. 필요한 프로젝트 공개 apikey는 인증된 회원 ID와 구분하고, 존재하는 Authorization user JWT가 무효하면 조용히 익명으로 강등하지 않는다. 로그인 bind/admin에는 검증된 user JWT를 요구하고 worker에는 별도 내부 비밀을 요구한다. 기존 함수 설정을 복사하거나 최신 `@supabase/server`로 전체 앱을 업그레이드하는 것은 이 검토의 권고가 아니다. 실제 키와 게이트웨이 설정으로 CORS/익명/user/internal 네 경로를 검증한다. [Supabase 함수 인증 모드](https://supabase.com/docs/guides/functions/auth)

### 2.6. 서버의 active 상태를 현재 OS 권한이라고 단정하지 않기

브라우저에서 권한을 철회해도 서버가 그 순간 반드시 알 수 있는 것은 아니다. active는 `마지막 확인에서 등록 가능했던 구독`의 서버 상태이고 provider 접수도 현재 화면 표시를 의미하지 않는다. 관리자 대상 집계는 확인 가능한 구독 건수이며 실제 수신 가능한 기기 수라는 단정은 피한다. [Web Push 접수 의미](https://datatracker.ietf.org/doc/html/rfc8030#section-5)

`pushsubscriptionchange`는 주요 브라우저 전체에서 지원되는 이벤트가 아니며 expirationTime은 null일 수 있다. 첫 실행·로그인 변경·온라인 복귀·포커스 복귀 때 실제 permission/getSubscription과 서버 상태를 합치는 동기화가 기본이고, 변경 이벤트는 보조다. 동기화가 실패하면 로컬에 필요한 변경 의도만 남기고 다음 온라인 실행에서 재시도한다. 권한창을 자동 재요청하거나 비활성 서버 행을 permission=granted만 보고 active로 되살리지 않는다. [변경 이벤트 지원](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/pushsubscriptionchange_event), [구독 만료 값](https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/expirationTime)

첫 안내는 `권한 허용`, `등록 확인 중`, `등록 확인 실패/다시 확인`, `등록 완료`를 구분해야 한다. 현재 미리보기는 버튼 클릭 직후 완료 상태로 바뀌는 가상 예시여서 중간 실패 화면의 승인을 대신하지 못한다. 실제 SW에서 확인 ACK가 실패한 경우 다음 앱 실행의 state 조회로 성공 여부를 대조한다. 설정 화면은 추가하지 않는다.

### 2.7. 재시도와 늦은 응답의 이력을 보존하기

현재 delivery의 attempts 숫자·최종 상태만으로는 `첫 시도 unknown → 관리자 재시도 → accepted` 경위를 복원하기 어렵다. 별도 `push_delivery_attempts`를 제안한다. delivery는 논리 대상 한 개이고 attempt는 외부 호출 한 번이다. `(delivery_id, attempt_no)`를 유일하게 하고 시작·HTTP 결과·종료 원인·재시도 수행자를 남긴다. payload·키·endpoint 원문은 보관하지 않는다.

외부 시작 CAS에는 현재 token뿐 아니라 `status=leased`, lease 미만료, attempt 일치, 종료/중단/TTL 조건이 함께 필요하다. 일시 정지됐던 worker가 점유를 잃은 뒤 다시 외부 전송을 시작하지 못하게 한다. 결과 저장에 실패한 accepted는 영속 시작 기록이 있으므로 unknown 회수하고 자동 재전송하지 않는다. 늦게 도착한 결과는 원래 attempt에만 귀속시키고 새 시도/최신 집계를 덮지 않는다.

안전한 retry의 external_started_at은 새 attempt에 별도 기록한다. 이전 시도의 시작값이 남아 새 점유가 잘못 unknown으로 회수되지 않도록 한다. 관리자 재시도도 자동/수동 합산 상한·현재 lease 없음·기존 TTL 이내 조건을 요구한다. completed 캠페인을 재시도한다면 processing으로 돌아가는 상태 전이를 명시하고 revision을 올린다. stopped는 원 캠페인에서 재개하지 않는다. 중복 가능 경고를 확인했다고 무제한 전송 권한을 주지 않는다.

provider 성공은 명시된 provider 계약의 성공 상태로 분류하고, 3xx는 리다이렉트를 따라가지 않는다. 401/403 설정 장애와 구독 철회를 혼동하지 않는 기존 방향을 유지한다. 5xx/timeout을 보수적으로 unknown으로 처리하는 정책은 재전송률과 함께 검증하고 provider별로 근거 없이 느슨하게 바꾸지 않는다.

### 2.8. 중단 완료와 관리자 권한 회수의 의미 정하기

중단 버튼 직후 `stopped`로 표시하면 이미 시작된 작업까지 끝난 것으로 오해할 수 있다. `stopping`을 추가하고 미시작 작업을 skipped로 확정한 뒤, 시작된 attempt가 accepted/failed/unknown으로 분류되면 stopped로 전환한다. 이미 서비스가 수락한 알림은 회수할 수 없다는 설명을 유지한다.

캠페인은 합법적으로 접수된 뒤 작성자가 화면을 닫거나 로그아웃해도 계속 처리한다. 다만 작성자 계정 탈퇴/정지·관리자 역할 회수 시 새 외부 요청을 차단하는 정책을 권고한다. 접수 때의 관리자 확인과 worker 시작 때의 역할 검사는 다른 책임이다. 역할 회수 후에는 이미 시작한 호출만 결과를 기록한다. 이 정책은 운영 규칙으로 설계에 확정해야 하며 미리보기 UI만으로 구현하지 않는다.

감사는 캠페인 접수/중단/재시도와 같은 트랜잭션에 남긴다. 개인 회원 검색·목록 조회 감사가 기존 운영 정책의 필수 조건이면 조회 결과와 감사도 같은 성공 경계로 처리한다. 마지막 페이지를 읽은 것만으로 첫 페이지의 개인 조회 감사를 대신하지 않는다.

### 2.9. 작은 장애가 전체 실패로 번지지 않게 하기

VAPID 키 오류, 특정 provider 429, registration challenge abuse에 대해 기기별 재시도만 있으면 같은 오류를 수천 번 반복할 수 있다. provider/키 조합 단위의 일시 중단·cooldown과 전역 발송 스위치를 분리하고 반복 오류에서 진단을 남긴다. 다른 정상 provider는 가능한 경우 처리한다.

캠페인당 10,000개만 제한하면 캠페인을 반복 생성해 전체 요청량을 늘릴 수 있다. 관리자별 접수/테스트 빈도, 전역 일일 요청·동시 작업 상한, 익명 pending/확인 알림 한도를 서버에서 제한한다. 구체적 숫자는 사용자 규모·허용 운영 비용으로 정하고 임의의 수치를 승인된 요구로 넣지 않는다.

암호화 데이터에는 key ID·인증된 암호문 형식·복구 절차를 둔다. 암호화키/VAPID 키 변경 때 기존 구독을 읽고 전송할 수 있는 이전 키 유지 기간이 필요하다. endpoint/설치 비밀을 URL·오류 body·분석 로그에 남기지 않는다.

현재 기록 보존은 논리 조회 90일과 실제 저장 기간이 분리돼 있다. 물리 정리를 도입하기 전까지 pending/disabled 자료와 감사가 계속 증가할 수 있으므로 저장량 관찰과 용량 상한을 마련한다. 이 검토는 자동 삭제를 실행하거나 보존기간을 확정하지 않는다.

별도 회원 알림 설정, 알림 종류 토글, 예약, 댓글 연동, 읽음률 수집은 이번 추천에 포함하지 않는다. 같은 사람의 브라우저/PWA 여러 구독을 추정해서 한 기기로 줄이지 않으며 endpoint 단위 중복 제거만 유지한다.

## 4. 최초 검토의 검증 시나리오와 진행 권고

구현 전 계약 검증에는 아래 경쟁/장애 시나리오를 추가한다.

- preview 이후 대상 감소/증가/동일 건수 대상 교체, 캠페인 요청 응답 유실 후 동일 idempotency key 대조.
- 타 설치의 pending 선점, register 직후 서버 종료, challenge 전송/ACK 응답 유실, 두 등록 확인의 순서 역전.
- A 계정 detach/B 계정 bind 경쟁, 동일 session 토큰 갱신, 사이트 저장소 유실, revoked 권한의 다음 실행.
- 암호화 지연·provider timeout로 작업 예산 소진, worker 종료/재점유/늦은 응답, 동일 unknown의 중복 수동 재시도.
- 캠페인 중단과 외부 시작 경쟁, 작성자 로그아웃과 역할 회수의 차이, provider별 429/키 오류·정상 provider 처리.
- 잘못된 URL·삭제된 게시글, 작은 휴대폰에서 최종 확인/회원 검색/진행 상태, 실제 iPhone 홈 화면 앱.

먼저 P1 계약을 정리하고 구독/기기 소유 확인과 worker의 작은 실연동 기술 검증을 한다. 그 결과로 초기 처리 규모·등록 복구 UI를 확정한 뒤 관리자 화면을 구현한다. 1,000/10,000개 부하 목표와 실제 지원 규모는 분리한다. UI 범위는 별도 승인하며 운영 쓰기는 승인된 테스트 범위에서만 수행한다.

최초 검토에서는 보고서와 본문 검토 링크만 추가했다. 후속 반영 작업에서는 설계 본문·관련 문서·분리 목업을 보완했다. 앱 코드·DB·배포 설정은 변경하지 않았다. 문서 링크·diff와 목업 가상 흐름 검증은 실기기/DB 검증을 대신하지 않는다.

Chromium 오프라인 목업에서 전체 발송 테스트 강제, 접수만 된 테스트의 확인 요구, 내용 변경 무효·대상 변경 재사용, 초안 저장/복원, 동일 발송 확인, 선택 회원 0개·선택 발송, 링크 검증, 진행/중단·합계, 등록 pending/실패/거절/iPhone 안내와 모바일 가로 넘침을 포함한 12개 묶음을 통과했다. 최종 확인 본문 추가 후 모바일 대화상자 스크롤·본문 일치·중단 진행을 추가 검증했다. 외부 요청·page error는 0개다.
