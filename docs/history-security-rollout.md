# 성적 이력 P1 수정의 운영 적용 절차

2026-09-28 로컬 수정안이다. 운영 배포·DB 변경·데이터 삭제·push를 수행하지 않았다. 수정 전 서버는 URL의 사용자 ID로 service-role KV에 접근하므로, 인증 없는 요청이나 다른 계정의 토큰으로 타인의 이력을 조회·추가·삭제할 수 있다. 수정본은 유효한 요청 토큰의 사용자와 URL 소유자가 일치할 때만 KV에 접근한다.

## 변경 범위와 검증

공식·사설 이력 8개 경로, 요청 토큰, 계정 전환 상태, 저장/조회 실패 안내를 변경한다. KV 키·스키마·기존 데이터·회독·그룹·API URL과 응답은 유지한다. 설정의 `verify_jwt = false`를 유지하며 함수 내부가 인증을 강제한다. DB·Storage·기타 서비스 기능은 변경하지 않는다.

`npm run check`는 프론트엔드 검사, Deno 타입/권한 없는 라우트 테스트, Supabase 요청을 모두 가로채는 브라우저 테스트, 빌드를 실행한다. 서버 테스트는 무인증·잘못된 토큰·타인 ID·Auth 장애가 KV에 도달하지 않는지 및 소유자의 기존 읽기/쓰기/삭제 계약을 확인한다. 브라우저 테스트는 조회 실패, 저장 실패 후 결과/입력 유지, 비로그인 채점을 검사한다.

## 배포 전 필수 확인

- 운영 원격 함수 버전·환경 변수 존재·KV grants/RLS·마이그레이션 이력을 읽기 전용으로 확인한다. 비밀 값이나 개인 이력을 보고서에 출력하지 않는다. 이번 로컬 작업에서는 원격 확인 도구가 없어 재검증하지 못했다.
- 격리 Supabase 환경 또는 사용자가 명시적으로 승인한 전용 테스트 계정·테스트 데이터로 실제 Auth/게이트웨이/CORS 경로를 확인한다. A/B 테스트 계정으로 무인증·만료·타 프로젝트 토큰 및 타인 ID 요청을 확인하고 소유자 CRUD·두 과목 그룹·회독을 검사한다. 기존 이용자 데이터는 사용하지 않는다.
- 브라우저는 기존 헤더인 Authorization과 필요 시 Content-Type만 보낸다. 실제 게이트웨이에 apikey가 추가로 필요하다면 현재 패치를 그대로 배포하지 않는다. CORS 헤더 호환성부터 별도 변경·검증한 후 클라이언트를 적용한다.
- Auth는 요청마다 원격 확인하며 8초 제한을 둔다. 사용자 이력 읽기/쓰기의 지연, 동시 요청, Auth 장애 시 503과 입력 유지, 정상 트래픽의 오류율을 확인한다. 클라이언트 fetch는 응답 본문을 포함해 20초 제한을 둔다. SDK 세션 갱신은 이 fetch 제한과 별개다.

## 두 번의 릴리스

이 전체 변경을 한 번에 main에 push하지 않는다. `supabase/functions/**` 변경이 포함된 main push는 Edge Function 자동 배포도 시작하므로 웹과 서버 적용 순서가 보장되지 않는다. 각 릴리스 전 버전을 올리고 해당 커밋에서 품질 게이트를 통과시킨다. 배포 실행은 별도 명시적인 요청이 필요하다.

1. **클라이언트 먼저:** App/페이지, `useUserHistory`, `historyApi`, 프론트엔드 테스트와 해당 문서만 별도 커밋/PR로 적용한다. `supabase/functions/**`와 레거시 서버 어댑터를 이 릴리스에 포함하지 않는다. Edge 파일을 필요로 하는 `test:edge` 스크립트·CI 변경도 두 번째 릴리스에 둔다. 기존 서버에서 로그인 사용자의 Bearer 토큰과 요청/응답 계약을 검증한다. 서버 취약점은 이 시점에는 남아 있다.
2. **서버 강제:** 새 클라이언트 적용과 승인된 환경의 검증을 확인한 뒤 등록 함수의 app/auth/index·Deno 설정/lock·테스트 및 레거시 어댑터·검증 명령/CI·문서를 적용한다. 함수 환경에 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, 기존 `SUPABASE_SERVICE_ROLE_KEY`가 있는지 확인한다. JWT 게이트웨이 설정이나 키 교체를 같은 릴리스에 섞지 않는다.

기존에 열린 탭은 anon 토큰을 계속 사용하므로 서버 강제 후 401이 발생할 수 있다. 일반 PWA 갱신만으로 탭 전체가 최신 코드가 되었다고 가정하지 않는다. 사용자에게 새로고침을 안내하고 전환 영향을 운영자가 수용할 수 있어야 서버 릴리스를 진행한다. 구버전 탭의 무인증 접근을 유지하면서 이 취약점을 닫을 수는 없으므로 모든 세션의 무중단을 보장하지 않는다. 무조건 자동 새로고침으로 답안을 유실시키지 않는다.

## 관찰과 중단·복구

라우트 템플릿·메서드·상태 코드만 요청 로그에 남긴다. 토큰·사용자 ID·답안은 로그에 추가하지 않는다. 예상되는 무인증 401/소유자 불일치 403과 정상 이용자의 실패를 구분하고 Auth 503, KV 5xx, 요청 지연을 관찰한다. 기존 기준 대비 정상 사용자 실패가 증가하면 추가 적용을 중단하고 원인을 확인한다.

복구본도 소유자 인증 경계를 유지해야 한다. 기존의 무인증 서버나 anon 클라이언트로 되돌리지 않는다. Auth/설정 문제는 정상 설정 복구 또는 인증된 직전 정상본으로 처리한다. 원인을 즉시 해결할 수 없다면 개인 이력 API를 일시 차단하는 편이 타인 데이터 노출보다 안전하지만, 이는 운영상 제한이므로 배포 전에 운영자가 대응을 결정한다. KV 스냅샷을 덮어써 롤백하지 않는다. 응답이 유실된 POST/DELETE는 먼저 이력을 확인하며 자동 반복하지 않는다.

KV 배열의 동시 read-modify-write 경쟁은 기존 구조의 제약으로 이번 P1 수정에서 해결하지 않는다. 세션 폐기 직후 모든 JWT가 즉시 무효화된다는 보장도 하지 않는다. 최종 운영 조치 완료 판정은 실제 배포 및 위 통합 검증 이후에만 한다.

## 2026-09-29 릴리스 준비 확인

운영 함수는 version 8, ACTIVE, verify_jwt=false이다. 필요한 기본 환경 변수 이름을 확인했고 비밀 값은 조회·출력하지 않았다. KV는 RLS가 활성화되어 있으며 정책은 없고, anon/authenticated/service_role의 테이블 grants가 존재한다. 마이그레이션 메타데이터는 읽기 전용으로 확인했다. 공개 health는 200, 브라우저 OPTIONS는 204이며 기존 Authorization/Content-Type 헤더를 허용한다. 개인 이력 조회와 운영 쓰기는 수행하지 않았다.

프론트엔드 v1.4.4는 커밋 `54751e8a`로 main에 push했고 Vercel production 배포가 성공했다. 공개 HTML과 JS가 검증한 빌드와 바이트 단위로 일치한다. 사용자가 운영과 분리된 검증 프로젝트가 없다고 확인했으므로 서버 수정은 별도 커밋으로 보존하고 배포는 보류한다. 프론트엔드만 적용한 상태를 P1 해결 완료로 판정하지 않는다.

## 2026-09-29 서버 릴리스 v1.4.5 검증

v1.4.4 웹 배포 이후 사용자가 서버 배포와 배포 후 확인을 요청했고, 전용 테스트 계정 생성·테스트 이력 저장·정리를 명시적으로 승인했다. 두 전용 계정으로 후보 서버의 실제 Supabase Auth와 KV를 연결한 45개 검사를 통과했다. 공식·사설 이력의 소유자 CRUD, 8개 경로의 무인증·잘못된 토큰 401과 다른 계정 403, 두 과목 그룹·회독을 확인했다. 후보 검증 직후 테스트 KV 행을 삭제하고 부재를 확인했다. 기존 이용자 이력은 조회하거나 변경하지 않았다.

CI의 320px 홈 화면은 운영체제 글꼴 차이로 헤더 버튼이 한 줄에 들어가지 않아 348px 가로 넘침이 발생했다. 작은 화면에서 비로그인 버튼을 세로 배치하도록 수정하고, 기존 가로 넘침 검사 기준은 유지한다. 전체 품질 게이트와 원격 CI 통과 후 main에 적용하고, 배포된 실제 게이트웨이 및 웹에서 같은 전용 계정으로 검증한다. 모든 검증 이후 테스트 세션·계정·KV 행을 정리한다. 구버전 탭은 서버 인증 강제 이후 새로고침이 필요할 수 있다.
